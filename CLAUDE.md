# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Mochi UI: a custom Flutter UI kit built on `package:flutter/widgets.dart` only — **no Material or Cupertino** (`uses-material-design: false`). Every widget, theme, and interaction state is implemented from primitives. Dependencies: `tabler_icons_plus` (icons).

Status: early WIP. Public API is exported from `lib/mochi_ui.dart`. `lib/main.dart` is a preview gallery (every button intent × appearance × state, with a light/dark/system toggle), not a real app.

Design references: Bulma for component API (intents, appearances, breakpoint names), Catppuccin Latte/Mocha for colors, forui for typography scale and button/tappable API naming. Icons: Tabler (`tabler_icons_plus`). Corners are superellipses natively and circular arcs on the web, one token deciding (see **Corners**); components never name a border shape — they take `geometry.shape(...)` and clip with `MochiClip` — and never use `BoxDecoration.borderRadius`, except under a shadow, which is cast off a rounded rectangle (see **Shadows**). Press feedback grows (iOS style), never shrinks.

## Architecture

Split into `lib/mochi_ui/theme/` (data) and `lib/mochi_ui/widgets/` (UI).

Component roadmap and priorities: `ROADMAP.md` (tick items off as they land).

**Theme access.** `MochiThemeScope` (InheritedWidget) holds a `MochiTheme` (`colors`, `typography`, `touch`, extensions; value equality); read it via the `BuildContext` extensions `context.theme` / `context.colors` (`theme/theme.dart`). `MochiApp` / `MochiApp.router` take a `MochiThemeMode`, optional `lightTheme`/`darkTheme`, and `touch` (defaults to `MochiTheme.defaultTouch` by platform), and wrap content in `AnimatedMochiTheme` → `ColoredBox(background)` → `DefaultTextStyle` → `IconTheme` → `ScrollConfiguration`, so descendants get theme-derived text, icon, and scrollbar defaults.

**Colors (three layers).**
1. `theme/palette.dart`: raw hex values (`LattePalette`, `MochaPalette`). Not exported; only `colors.dart` may use it. Some Latte accents are darkened so text reaches WCAG AA 4.5:1 — re-check contrast when changing them.
2. `theme/colors.dart` `MochiColors`: semantic tokens. Neutrals (`background`, `surface`, `overlay`, `border`, `foreground`, `mutedForeground`) plus one `MochiTone` per `MochiIntent` (`neutral, primary, info, success, warning, danger`), looked up via `colors.of(intent)`. `MochiColors.light` / `.dark`.
3. Component styles derive everything from tokens. A `MochiTone` (`theme/tone.dart`) has `base` (fills/borders), `onBase` (text on base), `soft` (tinted bg), `onSoft` (intent text on soft or page bg). Hover/pressed colors are never stored; use `MochiColors.stateLayer(base, on, states)`. Nor is a muted version of each colour: `colors.muted(color, on:)` moves any colour a fifth of the way towards its ground (the page by default), which is how far `mutedForeground` sits from `foreground` in both palettes, and stops short of that where the full step would drop it under `minContrast` (4.5 by default; text on a fill like `primary.onBase` sits barely over that and hardly moves, so large text and icons pass 3) — opaque rather than an alpha, so it looks the same over a card as over the page.

**Typography.** Headings use the `title` typeface, not body at a heavier weight: Comfortaa's w600 beside its w400 is a whisper, so a heading set that way reads as one more line of the paragraph. That covers a dialog's and a page header's title, a collapsible's and an accordion's header, a toast's title over its description, and the small muted labels over a group of tiles, menu rows or sidebar items. What stays in the body face is everything that is a *label* rather than a heading: a field's label, a row's title in a tile, tree or sidebar, a button, a badge, the current step of a breadcrumb — there, weight is emphasis inside a line, not a change of role. `test/widgets/typography_roles_test.dart` holds that line, and checks the `wght` axis in `fontVariations` rather than the `FontWeight` beside it, since the axis is what a variable font actually reads. `MochiTypography` has two `MochiTypeface`s, `title` (w700) and `body` (w400), each with a Tailwind-based scale `xs3, xs2, xs, sm, md, lg, xl, xl2 … xl8` (`md` = 16px) and `scale(factor)`. Styles carry no color. Family is Comfortaa (variable font, wght 300–700) with FakePearl (假粉圓) as CJK fallback; both are bundled in `assets/fonts/` (OFL) and declared in `pubspec.yaml`. Change weight with `style.withWeight(FontWeight.wX)`, which sets `fontWeight` and the `wght` variation together. A typeface also takes `fontFeatures`, carried by every step of its scale and kept through `scale()`: that is where a readout asks for `FontFeature.tabularFigures()`, since most families space their digits proportionally and a timer set in one shuffles sideways as it counts. An app that wants a face of its own — a timer's, say — puts a `MochiTypeface` in a `MochiThemeExtension` and reads it as `context.theme.extension<AppTypography>()`, one mechanism for everything an app adds to the theme. Subclassing `MochiTypography` and passing it as `typography:` works too, and reads as `theme.typography.timer`: the theme swaps typography whole rather than interpolating it and compares it by identity, so a subclass survives both — but `scale` has to be overridden or it returns the base class and drops the extra face. What this kit does *not* have is forui's registry on the typography itself; that map exists there because `FTypography` interpolates and scales its own members, and here neither is true (text scales through `MediaQuery.textScaler`, and `MochiTheme.lerp` takes `b.typography` as it is).

**Branding.** An app that wants its own accent hands over one colour, not four: `MochiTone.from(base, background:, softAlpha:)` works out `onBase` (whichever of the theme's two inks reads on the fill, falling back to plain white or black when neither reaches 4.5:1 — the palette's inks are softer than either and a mid-toned accent leaves them short), `soft` (the accent over the page at `softAlpha`) and `onSoft` (the accent moved along its own lightness until it reads against the page, hue and saturation untouched: the answer to a blue that is too pale is a darker blue, not another colour). `MochiColors.branded({brightness, primary, info?, …})` is that applied to one of the two themes, keeping the neutrals — page, surface, border, text — which are what was tuned against each other in the first place. The arithmetic lives in `theme/contrast.dart`, which is not exported, for the same reason `palette.dart` is not. Two things it deliberately does not do: take Material's `ColorScheme` (this kit imports no Material), and derive the semantic intents from one seed, since green has to stay green.

**Geometry.** `MochiTheme.geometry` (`MochiGeometry`): `radius` (xs 6 / sm 8 / md 10 / lg 14 / xl 20 / full), `space` (xs3 2 … xl3 64), `shadows` (sm/md/lg layers, colored by `colors.shadow` via `shadows.of(elevation, color)`), `borderWidth`, `focusRingWidth`/`focusRingGap`, `pagePadding`. Components take sizes, radii and shadows from here rather than literals. Size-dependent metrics reference tokens through functions (e.g. `MochiButtonMetrics.radius` is `BorderRadius Function(MochiRadius)`).

**Layering.** `MochiTheme.layering` (`MochiLayering`: `outlined`, `raised`) is how a surface is told apart from the one under it, and it follows `touch` unless `MochiDefaults.layering` says otherwise: a phone's cards stand off the page, a desktop's are drawn with a line. It is a shadow and not a colour: a first try at Catppuccin's surface0/1/2 as steps of fill looked wrong, and a card *darker* than its page with a shadow around it only grades from one grey into the next with no edge between them. So a `raised` elevated card is `colors.overlay` (lighter than the page in both themes), has no line even when chosen (its tint, `_raisedTint` times a soft fill's alpha, says so), casts the shadow one step deeper than its `elevation` and is `radius.lg`. In the dark theme a black shadow is invisible on a dark page, so the card also wears a pale halo (`MochiShadows.raised`, shared with the bottom bar, white at 0.5, blur 12 — a wider halo ran together between cards set side by side): a 1px highlight along the top edge was tried and read as odd, and a halo at 0.12 or 0.22 was too faint to see. A `soft` card in the same theme is rounder and loses its line but casts no shadow, being a note rather than a container; `outlined` is its line and never changes. A tile group is one raised block the same way (rows are mixed over the group's fill, handed down by `_TileGroupScope`, not over `surface`), and its dividers stay. A dialog, sheet, popover and toast are too (they were already `overlay`; they lose their line and take `MochiShadows.raised`), except that a toast with an intent keeps the intent on its edge and a tooltip is left alone — an inverted little bubble with a halo would look odd. A `MochiHeader` with no `variant` of its own follows suit: floating when raised (the floating bottom bar's look and margins — `overlay`, no line, `radius.xl`, `space.md` clear of the sides, `space.xs` under the status bar — so the two line up), plain when outlined; one asked for is kept either way. The bottom bar is lit the same way, in `overlay` with the shadow cast upwards and no line along its top. Fields keep their line and get no shadow. Layering is *not* what decides between a popover and a sheet: that is the width (the breakpoint `showMochiModal`, the date picker and the select share), and the two are kept apart on purpose — a tablet is touch with room under a field, a narrow desktop window is a pointer without it, so one is raised with popovers and the other outlined with sheets. Layering answers what a surface looks like; the width answers where a list has room to go. Plan and what is left: `docs/plans/layering.md`.

**Flutter channel: stable 3.47.4 (pinned in `.fvmrc`).** The project followed master for a while, because stable 3.47.x renders strokes and paths on Linux without antialiasing: Impeller's SDF renderer has no `drawPath` antialiasing (flutter/flutter#185117, still open) and relies on MSAA, which the Linux embedder did not enable until PR #191379 (flutter/flutter#191171), merged to master 2026-08-23 and not in 3.47.x. It came back on 2026-09-26 for a worse fault the other way: **master draws long gradients wrong.** Impeller there bakes a gradient into a lookup table of 256 texels and then walks it at `length / 256` texels a pixel instead of `256 / length`, so any gradient longer than 256 device pixels reaches its last colour after `65536 / length` pixels and is flat the rest of the way. Measured on Linux at dpr 1 with a plain `BoxDecoration(gradient:)`: 400 wide ends at 164, 480 at 137, 640 at 102, 800 at 82 — `width × end` is 65536 every time, and everything 256 and under is right. A colour picker is nothing but long gradients, and stair steps on a curve are easier to live with than a hue bar that is flat red for three quarters of its length. Two things to know about that trade. The stair steps are accepted rather than worked around: the old workarounds (a custom fill+clear superellipse border, a sweep-gradient spinner) stay removed, since the MSAA fix is already in master and will arrive in a stable by itself. And nothing else holds the pin down — `RawMenuAnchor`, `RawTooltip`, `RadioGroup`/`RawRadio`, `ReorderableList.onReorderItem` and `OverlayPortal.overlayChildLayoutBuilder` have all shipped in 3.47.4, whatever the notes below still call master-only — so the moment a stable carries both the MSAA fix and a gradient that is not broken, move the pin forward and check both: a rounded border for stair steps, and a wide `MochiColorPicker` for a flat hue bar.

**The test harness cannot see what Impeller does.** `flutter test` rasterises with Skia, so a golden or a pixel read in a widget test is a check of the *arithmetic*, never of what the app draws. Both of the colour picker's rendering faults — a track collapsed to nothing and a gradient that stopped a quarter of the way along — passed every test and every golden. What found them: a throwaway `lib/main_gradient.dart` with nothing in it but the thing in question, run on the real device, printing its own measurements (paint into a `RepaintBoundary`, `toImage`, read the bytes, show the numbers on screen) rather than leaving them to be guessed off a screenshot. Measure on the device, and compare the same probe across SDK versions before blaming the code.

**Corners.** `MochiGeometry.corners` (`MochiCorners.superellipse` / `.rounded`) is the curve of every corner, and it is a token because the web cannot afford the first one: CanvasKit and Skwasm have no superellipse of their own and draw one as an arbitrary path, and a clip along a path is the expensive part. On an iPhone (Vivaldi, release, both renderers) a page of the kit sat at 60–70ms of raster a frame whatever its layering, and the same page with every superellipse swapped for a rounded rectangle ran at about 6 — native Impeller draws a superellipse as a primitive and should not pay this, which is still to be measured on a native build. So `MochiCorners.platform` is `rounded` on the web and `superellipse` everywhere else, and `MochiApp(corners:)` / `MochiTheme.copyWith(corners:)` override it. Components ask `geometry.shape(borderRadius:, side:)` for a border and wrap clips in `MochiClip` (exported, reads the theme with a fallback); `test/theme/corners_test.dart` fails on a `RoundedSuperellipseBorder(` or `ClipRSuperellipse(` written into `widgets/`, and the gallery smoke test walks every page with circular corners for one left behind. What found it: a copy of the repo with the two names replaced by text, built for the web and opened on the phone beside the real one — measure the swap before building the switch.

**Shadows.** A `ShapeDecoration` never carries `shadows`: a surface's shadow goes on a `ShapeShadow` (`widgets/shape_shadow.dart`, not exported) around it, which is a `BoxDecoration(borderRadius:, boxShadow:)` — a rounded rectangle under the superellipse. A blur along an arbitrary path is drawn by blurring the whole shape, every frame on the web, which has no raster cache, while a rounded rectangle has a fast analytic blur, and under a blur the two outlines cannot be told apart. Measured with a release web build in headless Chrome at phone size (the throwaway `lib/main_scaffold.dart` with `?auto=1`, which prints a line per phase): a raised page with a 30-row tile group scrolled at 52ms of raster a frame, about 18 frames a second, and at 16ms once the group's shadow moved — the outlined page is 10 to 13. What it looked like on a phone was everything sluggish, presses included, which is what a raster thread that never catches up does. `test/gallery_smoke_test.dart` walks every page in both layerings for a `ShapeDecoration` with shadows, so one put back turns up there. `ShapeShadow` builds the same box with or without shadows, so a layering switch does not remount what is under it.

**Antialiasing.** Never stroke a shape with the same color as its fill: the antialiased edge is painted twice and hardens into stair steps. Filled button appearances therefore keep a fully transparent `BorderSide` (which also keeps the 1px layout).

**Soft fills on surfaces.** `MochiTone.soft` is mixed over the *page background*. A selected row inside a card sits on `colors.surface` instead, where that fill is too dark to read: use `colors.softOn(tone, background)` there. The dark theme carries more accent (`softAlpha` 0.26 vs 0.14) because pastel accents wash out over a dark ground.

**Opaque row backgrounds.** A row inside a clipped, bordered container paints over that container's border. Fading the whole row (disabled rows, for instance) lets the border show through and reads as an extra outline around that one row: dim the row's content, never its background.

**Icons.** Components only draw the icons in `MochiTheme.icons` (`MochiIcons`); anything else comes from the app. Adding an icon to a component means adding a token, not importing an icon set.

**Strings.** Same rule for words: components only say what is in `MochiTheme.strings` (`MochiStrings`: the plain words `ok`, `cancel`, `back`, `close`, `dismiss`, `openMenu`, `remove`, `listSeparator`, `reorder`, `search`, `clear`, `reset`, `expand`, `collapse`; a calendar's and a picker's `months`/`monthsShort`/`weekdays`/`monthYear`/`date`/`dateRange`/`pickDate`/`pickTime`/`am`/`pm`/`previousMonth`/`nextMonth`; a pagination's `pagination`/`previousPage`/`nextPage`/`pageNumber`/`goToPage`; a colour picker's `pickColor`/`hue`/`opacity`/`shade`/`hex`; and a text field's `cut`, `copy`, `paste`, `selectAll`), and labels an app passes in are its own. The ones that are functions rather than strings — `date`, `dateRange`, `monthYear`, `pageNumber` — are functions because word order is not the same in every language. A literal an English speaker would read is a bug: `test/theme/strings_coverage_test.dart` is not what catches it, a grep for a quoted capital letter in `widgets/` is. It is a theme token rather than a `LocalizationsDelegate` — an app picks `MochiStrings.en` / `.zhHant` (or its own) for its locale and passes `MochiApp(strings:)`. A label parameter that used to default to English is now nullable and resolves at use: widgets read `context.theme.strings`; `show…` helpers and routes, which run once rather than build and may sit outside a `MochiApp`, use `MochiTheme.maybeRead(context)` and fall back to `MochiStrings.standard`. The toast's close button names itself through `Icon.semanticLabel`, not a tooltip: the toaster is above the navigator, so there is no `Overlay` for a tooltip to float in.

**A ring is for the keyboard.** `MochiTappable` shows `WidgetState.focused` only when three things hold, and any of them can change without the others. The framework wants a highlight; *this* is the thing focused rather than something inside it (`hasPrimaryFocus`, or a row would wear a ring because a button in it is focused — two rings for one focus); and the focus was not taken by a pointer. That last one is the web's `:focus-visible`, and Flutter cannot answer it: on a desktop a mouse and a keyboard are both `FocusHighlightMode.traditional`, so a click leaves a ring nobody asked for — most visibly on a popover's anchor, which `RawMenuAnchor` hands the focus back to when the panel closes. A private `_LastInput` watches the pointer router and the keyboard for which kind spoke last; it is a `ValueNotifier` rather than a flag because the framework only reports a *change* of highlight, so something focused by a mouse and then reached by a key would never hear that it should be wearing a ring after all. The routes are reference-counted rather than registered once: a test binding clears the keyboard's handlers between tests, and a one-shot registration would be silently gone by the tenth.

**Focus ring.** Use `MochiFocusRing(visible:, radius:, child:)` for every focusable component. It paints outside the child (no layout change) and always builds a `Stack`, so toggling never resets the child's state. That `Stack` uses `StackFit.passthrough`: the default loose fit would hand the child the Stack's own constraints, so anything told to fill its width (a stacked dialog action) would shrink back to its content. Because it paints outside, any clipping ancestor (scroll view, clipped card) cuts it off: reserve `MochiFocusRing.outsetOf(context)` of padding around focusable content inside clipped areas.

**Entering and leaving.** `MochiSurfaceTransition` applies the theme's `transitionDuration` / `transitionCurve` (and the quicker reverse pair) as a fade, a fade with a slight scale, or a slide. `scrim: false` drops the dimming and the travelling shadow, which a page needs (it is opaque and shares a background colour with the one it covers) but a floating surface does not: a popover paints its own shadow throughout, and a modal's dimming belongs to the barrier behind it. Pages go through `MochiPageRoute` / `MochiPage`, which read those durations from the navigator's context (the navigator asks for them before `buildPage` runs). A `.slide` page can be dragged back by a 20px strip along its leading edge (touch and stylus only — a mouse has no edge to swipe from, and the strip would eat its clicks): the drag drives the route's own controller between `didStartUserGesture` / `didStopUserGesture`, the transitions go `linear` meanwhile so the page stays under the finger, and release goes through `maybePop` like a sheet's drag, so a `PopScope` that refuses settles the page back and hears about it. The gesture ends only once the page has arrived — putting the curves back mid-flight makes it jump. Nothing in the transition may change the tree's shape when it starts moving (`_EdgeShadow` keeps an empty `DecoratedBox` at rest): a new parent remounts the subtree and the drag is lost after its first update. Overlays are meant to reuse the same widget, so a dialog, a popover and a pushed page move alike. Which of the three a page or a dialog uses is a token, `MochiDefaults.transition` (the enum lives in `theme/motion.dart`, beside the durations it is played at): the routes take it when they are given no `transition` of their own, so an app that wants everything to fade says so once. A sheet and a popover do not ask — a sheet slides in from its edge and a popover grows out of its anchor, and that is what makes them those things rather than a setting.

**Motion.** `MochiTheme.motion` (`MochiMotion`) holds `stateDuration`, `themeDuration`, `sizeDuration`/`sizeCurve` (eased at both ends: a size that leaves rest at full speed reads as a jolt, since no gesture is driving it), the transition pair, and press springs. `MochiTappable(scaleOnPress: true)` wraps content in `MochiPressScale`, a render object that scales around the center while pressed (capped at `pressScale` and `pressMaxGrowth` px per side), springs back with overshoot, keeps quick taps visible for ≥90ms, snaps exactly to rest, and honors `MediaQuery.disableAnimations`. It repaints per tick without rebuilding; turn it off for list rows. It reads the theme with a fallback, so tappables work outside `MochiApp`.

**Appearance knobs.** `MochiApp(radius:, density:, textScale:)` apply to both themes. `radius` takes a `MochiRadius` preset (`sharp`, `subtle`, `standard`, `rounded`, `pill`, or `MochiRadius.scaled(f)`; `full` never scales). `density` is `MochiTheme.density`: the theme keeps the geometry it was given and exposes `theme.geometry` with the spacing and page padding already multiplied, and the metrics of buttons, close buttons, badges, tiles and menu rows multiply their heights and paddings — never text, icons, corners or lines. Because `theme.geometry` is the scaled one, never pass it back through `copyWith(geometry:)` (it would be scaled twice); change corners with `copyWith(radius:)`. `density` switches immediately in `MochiTheme.lerp` (the metrics transitions ease the sizes anyway), so it doesn't break the value-equality shortcut described under theme animation. `textScale` is not a typography scale: `MochiApp` multiplies `MediaQuery.textScaler`, so it compounds with the system's setting and reaches every `Text` below, the app's own included.

**Theme extensions.** App-specific theme data subclasses `MochiThemeExtension<T>` (implement `lerp`; add `==` if the extension is rebuilt per build) and is read with `context.theme.extension<T>()`. `copyWith(extensions:)` merges by type.

**Theme animation.** `AnimatedMochiTheme` fades the whole `MochiTheme` via `MochiTheme.lerp` (colors and extensions interpolate; typography, geometry and `touch` switch immediately). Any new field added to `MochiColors` or `MochiTone` must also be added to its `lerp` **and to its `==`/`hashCode`**: value equality all the way down is what makes `MochiTheme.lerp(from, to, 0) == to` true when a change touches none of the interpolating parts, which is how a `touch` flip is applied in one frame instead of rebuilding the whole app for 200ms to paint the same colors. Without it the measured frame rate on a busy page fell to ~12fps (build 25-75ms per frame); with it, 60fps at 4-7ms. `MochiTheme` must keep value equality for the same reason, otherwise every `MochiApp` rebuild restarts the animation. The blend is computed at `t == 0` too, so the immediately-switching fields are not held back by a frame. Under `MediaQuery.disableAnimations` it exposes the target theme directly.

**Measuring frames.** Judge motion from `SchedulerBinding.addTimingsCallback`, not from watching: log `buildDuration`, `rasterDuration` and the gap between `FramePhase.vsyncStart` timestamps. A steady 16.7ms gap is 60fps; 33.3ms means every other frame is being dropped even though each one looks affordable. Debug builds inflate build time roughly 5x, so compare like with like.

**Disabling.** A field takes `enabled` *and* treats a null callback as disabled — text field, select, stepper, OTP, search bar, slider, switch, checkbox and the pickers all have both, so a form can grey one out without dropping the handler it will want back. Bodies and rows (a calendar, a time wheel, a pagination, a tree) disable through their callback alone, since there is nothing in them to grey out on its own. Whatever the knob, the rule underneath is `MochiTappable`'s.

**Interaction states.** `MochiTappable` is the base for all pressable widgets. It owns a `WidgetStatesController` (hovered / focused / pressed / selected / disabled), wires gestures, keyboard activation (Enter/Space → `onPress` only), focus, cursor, and semantics, and exposes states through a `ValueWidgetBuilder<Set<WidgetState>>`. Disabled = `enabled: false`, or all of `onPress`, `onLongPress`, `onDoublePress`, `onSecondaryPress`, `onSecondaryLongPress` are null. Gesture callbacks are passed to `GestureDetector` only when non-null — in particular a registered `onDoublePress` delays `onPress` by the double-tap timeout. `onPressDown` / `onPressUp` / `onPressCancel` are the two ends of a press and the one that was called off, in that order (`up` arrives before `press`, which is what the recognizer concludes from the two). They are the *tap recognizer's* edges, not the pointer's: with anything else competing for the gesture — a scrolling page, most often — they wait for the arena to settle, which can be 100ms or as long as the press. Anything measuring the press, a stopwatch started by touching the screen, wants a `Listener` and its raw `onPointerDown`; `MochiStepper`'s hold-to-repeat is the kit's own example. `selected` is owned by the widget: a `statesController` passed in gets `selected`/`disabled` overwritten from widget params. A press that belongs to a tappable *inside* another one does not tint the outer: both recognizers stay in the arena until the finger lifts, and both are told the press began once it passes `kPressTimeout`, so a button in a row used to make the whole row flash and only the release took it back. The innermost claims the pointer — a pointer-down is dispatched along the hit path from the deepest out — and the ones above it stand down for that pointer only. Visual widgets (e.g. `MochiButton`) build on it and resolve colors from the state set.

**Button styles.** Color intent and visual appearance are separate axes: `MochiButton(intent:, appearance:)`, where `MochiButtonAppearance` is `solid, soft, outlined, ghost, text, inverted`. `MochiButtonStyle.of(intent, appearance)` (`theme/styles/button_style.dart`) returns state-resolving color functions `(MochiColors, Set<WidgetState>) → Color`. Selected steps the appearance up one level (text/ghost/outlined → soft, soft/inverted → solid, solid → deepened); outlined keeps its border. `prefix`/`child`/`suffix` are laid out in a `Row`. Layout comes from `MochiButtonMetrics.of(size, touch:)` (heights desktop 28/32/36/40, touch 32/40/44/48); `MochiButton.icon` is square with width = height. Don't set `Container.alignment` on the surface — it makes the button fill its parent. Disabled is rendered as 40% opacity on the whole button; the focus ring is painted outside the box via a `Stack` so it never shifts layout. A button that is waiting is not disabled: `loading` puts a `MochiCircularProgress` the size of the button's icons over the label, which stays laid out underneath at zero opacity — the button is the same width before, during and after, and nothing beside it shuffles — and the 40% fade is skipped, since a faded spinner reads as broken. `MochiButton.async` is the same thing with the waiting owned by the button: it runs the future, refuses a second press while it is in flight, reports a failure through `FlutterError.reportError` rather than swallowing it, and puts the label back in a `finally` however it ended. Which one to use is a question of who else cares: `loading` when the app already holds that state (a form disabling several things at once, an errand that can also be started elsewhere), `.async` when the button is the whole story. The border is always present (transparent when unused) for the same reason.

**One way to turn a chevron.** Every chevron that flips — a collapsible's, a select's, a tree row's — is a `Transform.rotate` driven by the transition that is already running for that component (`MochiStateTransition` or `MochiValueTransition`), with the angle in `math.pi`. Not `AnimatedRotation`: an implicit animation restarts on every frame of a theme change, which is the same reason the rest of the kit avoids `Animated*` inside components.

**State animation vs theme animation.** Inside components, don't use implicit `Animated*` widgets (`AnimatedContainer`, `AnimatedDefaultTextStyle`, …) for theme-derived values: every frame of `AnimatedMochiTheme` changes their target and restarts them. Use `MochiStateTransition` (`widgets/state_transition.dart`), which animates only when the `WidgetState` set changes and resolves colors against the current theme each build. Keep theme reads in the innermost widget (see `_ButtonSurface`) so interaction wrappers aren't rebuilt. When a color should fade in from transparent, use `color.withValues(alpha: 0)`, not `Color(0x00000000)` — lerping from transparent black flashes gray.

**Size animation.** The same restart problem applies to metrics, so sizes go through `MochiValueTransition<T>` (`widgets/value_transition.dart`): it eases between two values of any type over `motion.sizeDuration` and only restarts when the value itself changes, blending from wherever it currently is. The animated type needs value equality (`MochiButtonMetrics`), otherwise every rebuild counts as a change and the animation restarts forever. `MochiButton`, `MochiTile` and `MochiSwitch` use it for the `touch` ↔ desktop scale.

**Popover.** `MochiPopover` (`widgets/popover.dart`) is the base for menus, context menus and anything else anchored to a control. It wraps the widgets-layer `RawMenuAnchor`, which mounts the panel in an `Overlay`, closes it on an outside tap or Escape, and restores focus to the anchor — so the widget itself only adds placement and the surface. Placement is a `SingleChildLayoutDelegate`: a `MochiPopoverSide` × `MochiPopoverAlign` against the anchor rect, a flip to the opposite side when the preferred one has no room (and only when the other side is genuinely roomier, otherwise the panel jumps about as its content resizes), then a clamp inside the overlay. The anchor builder is handed a `MochiPopoverAnchor` (`controller`, `focusNode`, `toggle`); wiring `focusNode` into the control is what makes focus return. Two panels at once is almost never meant, so opening one closes every open popover it did not come out of: a private registry of the open ones, and a `_PopoverScope` around each panel so a popover opened from inside another knows whose child it is — `RawMenuAnchor` puts a panel *beside* its anchor in the element tree, so a submenu has no ancestor to look up and would otherwise be treated as a second menu. Nothing else closes a panel when the next one opens by anything but a plain tap: a secondary tap is not an outside tap, which is how a row with both a context menu and a ⋮ ended up with one of each standing. A `MenuController` belongs to one anchor — the framework asserts on a second — so an app cannot solve this by sharing one, and would otherwise need a controller per row.

`scrim` (defaulting to `theme.touch`) dims the page behind the panel and swallows the tap that dismisses it. A phone is small and busy, and a panel floating over a dense list with nothing between them reads as part of it; a pointer has a cursor to say where it is and a screen with room to spare. Only the outermost popover draws one, or a submenu would dim the menu it came out of. Swallowing the dismissing press is not the scrim's job alone: `consumeOutsideTaps` is on by default on every platform, since a press aimed at "away" that also chooses a row or follows a link is not what anybody meant by it, and both desktop toolkits agree. It costs a second press to move from one row's menu to the next, which is the right way round — one of those presses is a mistake far more often than it is a shortcut. The anchor is the other half of the same rule: while its panel is up, a `closeOnAnchorPress` anchor absorbs pointers in its own subtree, so pressing the row a context menu belongs to puts the menu away and does not also choose the row. The `Listener` that closes it sits above the absorbing box, so it still hears the press; the cost is that a second right click closes rather than moving the panel to the new spot, which is the same press doing one thing. `open(position:)` places the panel at an offset from the anchor's top left instead of against an edge, which is how a context menu opens at the pointer. Entering and leaving go through `MochiSurfaceTransition(scrim: false)` growing out of the anchored corner, and the overlay stays mounted until the exit animation finishes (`onCloseRequested` holds `hideOverlay` back).

**Menus.** `MochiMenu` (`widgets/menu.dart`) is a column of `MochiMenuItem`s (plus `MochiMenuDivider` / `MochiMenuLabel`) sized to its widest row by `IntrinsicWidth` and scrolling once it runs out of room. Rows sit `space.xs3` apart, so two chosen rows side by side (a multi-select's) read as two fills rather than one block; every list here goes through `MochiMenu`, so that one gap covers selects, autocomplete, context menus and the text field's menu. `MochiPopoverMenu` is the dropdown form, `MochiContextMenu` opens the same rows where the pointer is (right click, or long press — a child with its own long press wins the arena), and `MochiSubmenu` is a row that opens a menu beside it. An item runs its handler and then closes the *root* menu, found through a private `_MenuHost` that only the outermost menu installs, so choosing something in a submenu puts the whole thing away. On a phone a `MochiPopoverMenu` or `MochiContextMenu` puts its rows in a sheet instead (`sheet:` overrides the width rule; the menubar and the select pass false): `MochiPopover.sheetBuilder` takes over in `onOpenRequested`, so the anchor's `open`/`toggle` are the same calls and the controller simply never opens. A row there closes the sheet through `MenuHost`, and a `MochiSubmenu` in a sheet opens its rows in place under itself through `MochiReveal`, since a sheet has no "beside" for a second panel. Rows take a `MochiIntent`: anything but neutral is tinted at rest, not only while hovered, since the colour is what marks a destructive action out.

Two things about keys and menus, both from `RawMenuAnchor` putting the panel *beside* the anchor in the element tree rather than under it. First, arrow-key traversal is installed around the anchor, so a submenu's open key must be bound inside `MochiPopover.builder` (below that traversal, where the nearest binding wins) while its close key must be bound above `MochiPopover` (where the panel's own key events travel). Second, a `Shortcuts` or `CallbackShortcuts` placed inside the panel is *below* the focus that the panel takes, so it is never consulted. In tests, a touch tap leaves `FocusManager.highlightMode` in touch mode, where hover highlights and arrow traversal into a menu don't happen: open with `tester.tap(..., kind: PointerDeviceKind.mouse)`, and reuse one mouse gesture rather than adding a second pointer for the same device.

**Actions.** `MochiAction` (`widgets/action.dart`) is what a bar of actions is made of: an icon, the words for it, and what pressing it does. A *value*, not a widget, because the same action is drawn two ways — an icon button while there is room, a menu row once there isn't — and only a value can be drawn twice; the same reason `MochiSelectOption`'s label is a `String`. That label is the menu row's text, the button's tooltip and its name in semantics at once, so an icon-only action cannot be nameless. `showLabel` writes it out beside the icon (a switch has to say which way it is about to go), `selected` tints the button and ticks the row, and `MochiAction.back` / `.close` take their icon and words from the theme the way every other component does. `MochiAction.menu(children:)` opens a menu instead of doing something, and its rows are `MochiAction`s rather than widgets for the same reason: with room it is a button opening a `MochiPopoverMenu`, folded into the … it is a `MochiSubmenu` with the same rows. It has no `onPress`, so it counts as disabled when it has no children, not when the callback is null.

`MochiActionBar` is the row, and it folds: with more actions than it has slots, the last slot becomes a … opening a `MochiPopoverMenu` of the rest, so the row is the same width whatever it is given — the bargain `MochiPagination` makes with its numbers. The cap is a *count*, not a measurement, for a reason: the bar sits at one end of a row whose middle is the flexible part (a header's title), so it is handed an unbounded width and has nothing to measure against. It defaults by breakpoint — two slots on a phone, four above it — since the breakpoint is what the rest of the kit uses to decide how much fits, and `maxVisible` overrides it. `scaleOnPress` is the caller's to say: a bar at the top of a page wants the growth, one tucked inside something with a border of its own — a field's suffix, a card's title row — does not, since there the growth reads as the box itself moving, and the bar cannot tell where it has been put. `dense` squares the buttons down to their icons (`iconSize + 6`, with no padding beside them), so a bar sits inside a line of text without making it taller: even an `xs` button is 28 against a heading's 20, so a card's title row grew by 4 to 10 pixels the moment one was added. It trades the target for a row that does not move, which is worth it beside words and nowhere else. The bar's own box is the bar's, gaps included: a fill layer *behind* the buttons takes the presses that land between them, or they go to whatever is holding the bar — inside a `MochiSearchBar`'s suffix that is the field, whose gesture detector covers the whole box on purpose, so a press aimed at a button and a pixel wide of it put the caret in the text and lit the field's ring. A detector that defers to its child is never hit in a gap at all, which is why the layer is there rather than a wrapper; and it takes taps rather than claiming the gesture eagerly, so a drag that starts in the bar still scrolls whatever is behind it. `MochiHeader` takes `List<MochiAction>` for both groups (with `maxVisibleActions` and `actionSize` handed to both bars, one size for the whole bar) and there is no `MochiHeaderAction` any more: one vocabulary, and a header action that is only a widget cannot become a menu row when the bar runs out of room. A `.center` header title is centred on the whole bar, not on the room between the groups (a private render box, since a `Row` can only centre in what is left, which moved the title whenever an action came or went); a title too long for that slides clear of the wider group and only then ellipsizes.

**Modals.** `MochiDialog` (`widgets/dialog.dart`) is the box; `MochiSheet` (`widgets/sheet.dart`) is the panel anchored to an edge. Both are shown by a `PopupRoute` (`MochiDialogRoute` / `MochiSheetRoute`) that reads its motion and barrier colour from the navigator's theme the way `MochiPageRoute` does, and enters with `MochiSurfaceTransition(scrim: false)` — the route's barrier does the dimming, over the whole screen rather than the surface's own box. Actions go in a row on the desktop scale and stack full width on touch, which is what apps otherwise wrap a dialog to do by hand. The title is optional: a modal is not always a question — a viewer, a picker, a panel with its own heading inside it — and one without a title draws no heading line at all, nor the gap that would have sat under it. What it cannot go without is a name, since the route announces itself, so `title: null` asserts unless a `semanticLabel` is given; a `titleSuffix` on its own (a lone close button) keeps the line and sits at its end. Both take a `title` and a `titleSuffix`, drawn by one private `ModalHeading` (`widgets/modal_heading.dart`) so the two can't drift apart in typeface, size or the gap under it; a sheet's heading stays put while its `child` scrolls. The `titleSuffix` puts a widget at the end of the title's own line: that is where anything that is *not* an answer goes — a close button, a `MochiActionBar`, or a control that changes what the modal is showing — since a button among the actions says it closes the modal, and a phone stacks those full width where anything else reads as a third way out. Both get out of the keyboard's way, which is the route's job rather than the surface's: the sheet route pads by `viewInsets.bottom` so the panel stands on top of the keys — without it a bottom sheet with a field in it is entirely behind them, and its half-screen cap is measured against room it does not have — and the dialog route adds the same inset to its padding, so the box centres in what is left. A sheet fills the screen across its own axis and shrink-wraps along it (so the column's `mainAxisSize` follows the axis), up to nine tenths of the screen: the cap only bites when the content is taller than it, so it never makes a short sheet taller — it decides whether a tall one is shown or scrolled through, and the last tenth is the strip of page behind that says this is a sheet and where to press to be rid of it. A side sheet keeps to half the width, since one covering the screen is a page, clears the system's edge padding itself since it runs to the edge, and dragging it towards that edge drives the route's own `AnimationController` backwards so the barrier fades with it. That drag goes through `maybePop`, not `pop`: a `PopScope(canPop: false)` inside the sheet refuses it the way it refuses the barrier and the back button, and hears about the attempt either way, which is where an app asks whether to discard what is in the sheet. A refused sheet settles back where it came from — only `RoutePopDisposition.pop` counts as leaving, since `bubble` hands the gesture to the platform without this route closing. The `Align` lives *inside* `buildTransitions`, not in `buildPage`: a slide moves its child by a fraction of that child's size, so with a full-screen wrapper in between, both the animation and the drag would be measured against the screen rather than the sheet. Dismissing needs 48px of travel as well as half the sheet, so a short one can't be flicked away by a twitch — and the gesture is longer than that, since the recognizer eats the touch slop before the first update.

`showMochiModal` picks between the two from the breakpoint: a dialog from tablet width up, a bottom sheet on a phone. It takes the *parts* of the question (title / body / actions) rather than a built widget, because the two containers lay their actions out differently — which is also why there is no `Dialog.adaptive`: what adapts is the presentation, not the component. `sheetConstraints` is how a modal asks for a *shorter* sheet than the default nine tenths; nothing in the kit needs one, since a sheet is only as tall as what is in it. `showMochiConfirm` / `showMochiAlert` / `showMochiChoice` / `showMochiPrompt` are the ready-made questions built on it, with `MochiModalAction` as the button that pops the modal with a value; none of them are named after a dialog, since on a phone they aren't one. `showMochiPrompt`'s field owns its `TextEditingController` in a `State`, not the helper in a `try/finally`: the returned future completes when the route is popped, but the exit animation is still drawing the field, so disposing the controller then would break it. `multiline` asks the same question as a paragraph — a comment, a note — growing from `minLines`; Enter then makes a line instead of confirming, and the button is the only way out, which it already was. It is a flag rather than a helper of its own because nothing else about the question changes, and that controller trap is the reason an app should not compose its own prompt to get one. Its body is padded by `MochiFocusRing.outsetOf`, since a modal's body scrolls and a scroll view clips the ring.

**Toast.** `MochiApp` installs a `MochiToaster` above the navigator, so `showMochiToast` reaches it from anywhere, a toast outlives the page that raised it, and it paints over a dialog. Intent shows in the border, not the fill, and brings its own icon from `MochiIcons`. Hovering cancels the dwell timer (an Undo has to survive the pointer arriving) and leaving restarts it; the returned `MochiToastHandle` dismisses early. The stack has one width (`geometry.toastWidth`) rather than one per toast, which would jump as a longer message came and went. Tunable from `MochiApp`: `toastAlignment`, `maxVisibleToasts`, `maxQueuedToasts`, `toastWidth`.

**A toast's exit is two movements, and the queue is the toasts themselves.** Toasts raised past `maxVisible` wait their turn rather than pushing the oldest out, which would drop one nobody saw, and the waiting ones are drawn past the end of the stack — the real toasts, each giving up a little width and showing only its trailing edge (`_DeckPlace`). Leaving then goes: it slides towards the edge with the stack untouched, and only then does its place close. The front of the queue is promoted the moment that slide starts, and *stands where it was* — opaque, at its own place's size — so what the slide uncovers is the toast itself rather than a blank space; it grows up into the stack over the second half, at the mirror of the closing curve, so the stack below the gap moves up by exactly what it takes at the end and nothing above the gap moves at all. The places behind it hold until it goes (`reserved`), then move up with it. Several leaving at once each come up from the place they were standing at, not all from the front.

**Motion you can't see is motion you can't fix.** X11 screenshots can't see the Linux window under Wayland, so work on the toaster went several rounds of plausible-sounding blind edits that were wrong. What settled it: a throwaway `lib/main_toast.dart` with nothing but toasts on a timer and the durations slowed to two or three seconds, run with `fvm flutter run -d web-server --web-port 8080 -t lib/main_toast.dart` and watched in a browser a frame at a time. Do that first next time, and slow the motion rather than trusting a glance at full speed: a 320ms slide that the eye reads as a jump can be measured frame by frame (log the animated value) and turn out to be perfectly continuous — a mid-flight change of target really does turn round from where it is. Two things make that hard to see: in **debug web** on a busy page a frame can take longer than the whole animation, so only its first and last positions are ever painted, and the desktop app's browser pane **produces no frames at all while it is hidden** (a frame counter reads 0), which makes every animation look instant. Judge motion in a visible pane, or with `fvm flutter run -d linux`, where the same slide showed a dozen intermediate frames. Two habits from the same episode: prefer `Edit` over scripted string replacement (a reformat silently breaks the match and the "fix" never lands), and check a new test actually fails without the fix.

**Text fields.** `MochiTextField` (`widgets/text_field.dart`) is an `EditableText` with `rendererIgnoresPointer: true` inside a `TextSelectionGestureDetectorBuilder`'s detector that wraps the whole box, so a tap on the padding focuses it too and clicks, double clicks, drags and right clicks select the way platform fields do. It takes a `MochiButtonMetrics` for its `size`, and the box has the button's height as a minimum with a single line centred in it, so a field and a button in one row line up — computing the padding from the text's line height came out a few pixels short. The context menu is `contextMenuBuilder` → `MochiPopoverSurface` + `MochiMenu`, placed by `DesktopTextSelectionToolbarLayoutDelegate` and wrapped in `TextFieldTapRegion`, so pressing an item doesn't count as a tap outside the field and steal its focus first; its labels come from `MochiStrings`, and it always lists the same four edits, greyed out when they don't apply, rather than rows that come and go with the selection (on Linux a right click outside the selection moves the caret first, so cut and copy would otherwise vanish). A single-line field has no vertical padding, only the minimum height centring it, so the clear button appearing can't make the box grow. On web the browser's own context menu takes over (Flutter's default), so check the menu in a test on a desktop platform, not in the browser. A synthetic Enter from a browser automation tool never reaches Flutter's hidden DOM input either, so `onSubmitted` looks dead there: dispatch a real `keydown` on `document.activeElement` from the console to try it. Touch selection handles are a small `TextSelectionControls` (a dot under each end), shown by the same rule `TextField` uses. The prefix, the clear button and the suffix are the field's *chrome*, and they take drags as well as presses: a real mouse click travels a pixel or two between down and up, which the field's own `TapAndDragGestureRecognizer` reads as a selection drag and wins the arena with — so pressing a button in the suffix put the caret in the text and lit the ring, at three pixels of travel and up. Taps are left alone, so a tap on the magnifier still focuses the field the way a tap on the padding does. They keep the box from tinting for them as well: the field's `MouseRegion` covers the whole box, ancestors always being on the hover path, so the chrome has to *tell* the field the pointer is on a button rather than on the text — otherwise moving the mouse towards an action in the suffix lights the border on the way, which reads as the field waking up for a press that was never meant for it. The whole box is a `TextFieldTapRegion` for the same family of reason: `EditableText` blurs itself on a tap outside, and a button standing in the field's own chrome is not outside. `textCapitalization` is the on-screen keyboard's business and nothing else's: it changes nothing on a desktop and nothing about text that is pasted or set in code, so a field that only accepts capitals needs an `inputFormatter` as well. It defaults to sentences on the multiline constructor, which is prose, and to none everywhere else, since a single line is as likely to be a hex code as a name.

**Field frame.** `MochiFieldFrame` (`widgets/field_frame.dart`) is the label above a box and the description, error or counter below it, shared by the text field, the select and the autocomplete so a form lines up and an app's own field can wear the same thing. It stretches its children to the width it is given and, with no bounded width to give (a row of code boxes, a select in a row), lines them up at the start instead: a stretched child under an unbounded width would be handed a tight infinite one.

**Selects.** `MochiSelect` / `MochiMultiSelect` (`widgets/select.dart`) share a private `_SelectField`: the box is a `MochiTappable` drawn like a `MochiTextField` of the same size (same metrics, border colours, label / description / error), and the list is a `MochiPopoverMenu` with `matchAnchorWidth`. Options are `MochiSelectOption`s with a `String` label, because the label is also what the field (or a multi-select's badge) shows. A row's check is always laid out and only faded in, so ticking a row in a multi-select can't widen the list. A multi-select shows its choices as badges, or with `display: .text` as one ellipsized line joined by `strings.listSeparator` (", " / "、"): the box then never grows, which a filter row or a toolbar needs, and taking a choice out is the list's job alone. Opening from the keyboard focuses the chosen row (`MochiMenuItem.autofocus`); opening with the pointer doesn't, or the row would show a focus ring nobody asked for. Telling the two apart is a `Listener` flag that is cleared in a microtask after the pointer's release, since the tap that opens the list fires after the `Listener` sees the up event. On a phone (the date picker's breakpoint) the list comes up in a sheet instead: a single select's row answers and pops it, through the same `closeOnPress` as in the popover — a row closes whatever `MenuHost` (`widgets/menu_host.dart`, not exported) is above it, which a popover menu sets to its controller and the sheet to `Navigator.pop` — and a multi-select ticks a draft in `showPickerSheet` that only leaves through OK, since a sheet is a route that builds once. With an unbounded width the field sizes itself to its longest option (a `TextPainter` measure behind a `LayoutBuilder`), like the stepper, so it doesn't change width with the choice.

**Tree.** `MochiTree` (`widgets/tree.dart`) draws its nodes nested — each node's row followed by its children in a `MochiReveal`, so a branch grows open and folds shut the way a collapsible's body does rather than appearing at once — and walks the same nodes flat for the keyboard, into the rows that are showing. Each row carries its depth and one flag per level above it — whether that level still has a sibling below — which is what the indent lines are drawn from; the lines are per row, so a folding branch clips them with everything else. Which nodes are open is a `MochiControl<Set<T>>`, `expanded:`, and so is an accordion's (`Set<int>`, by place), each reporting the whole new set. Rows are keyed by the node's value, and so are their focus nodes, so a row keeps the keyboard as the branches above it open and close. The arrows do what a tree's arrows do: up and down walk the visible rows, right opens a shut node and *then* steps into it, left closes an open one and otherwise hands back to the parent (mirrored in right-to-left). The chevron is its own target but sits in `ExcludeFocus`, since the row is the tab stop; a leaf keeps the chevron's width so its label lines up with its siblings'.

**Menubar.** `MochiMenubar` (`widgets/menubar.dart`) is a `MochiPopoverMenu` per word plus the one behaviour a bar of menus has that a single dropdown doesn't: once one is open, hovering its neighbour opens that one instead, at once and without a press, and the arrows walk along the bar (bound inside the anchor, below the traversal `RawMenuAnchor` installs). It keeps the open index itself, closing the standing menu before opening the next — two panels at once is not a menubar — and an `onClose` only clears that index when it is still its own, since by then the neighbour may already have claimed it. Hovering opens nothing while the bar is shut. The bar scrolls sideways when it is given less room than its words need: a menubar has nothing it can drop, since a menu that isn't there cannot be opened. The hover-to-switch test runs under `TargetPlatformVariant.only(TargetPlatform.linux)`: on the default touch platform the highlight mode suppresses hover callbacks altogether.

**Trails and pages.** `MochiBreadcrumb` (`widgets/breadcrumb.dart`) writes its last step as plain text marked `header` in semantics rather than as a link — it is where you already are — and folds the middle of a long trail into a `MochiPopoverMenu` behind a …, keeping the first step and the last two. `MochiPagination` (`widgets/pagination.dart`) is built from `MochiButton`s: the current page is `solid` in the intent, the rest are neutral ghosts, and the run is cut down to `around` pages either side of it. A gap of exactly one page is written out instead of hidden — a … takes the same room as the number it would cover, so hiding it buys nothing and costs a step. Pressing a … asks for a page number in a small popover (`jumpable`, on by default): the … stands for the pages the row folded away, so it is where asking for one of them belongs, and putting it there costs the row no width — which on a narrow page it has none of to spare. A number outside the run lands on the nearest end; a blank or unparseable one does nothing at all, since a typo is not an instruction to go anywhere. On a page too narrow for the whole row, the window gives way before the row does: `around` is reduced to what fits, and below the five slots it cannot do without (the two ends, the two gaps and the page you are on) the row scrolls sideways rather than painting over its neighbour. The row is the same width on every page: the slot count is fixed (`2 * around + 5`, the window growing at the ends to take back what a gap cost) and every slot is as wide as the widest page number, so paging through doesn't make the row breathe.

**Bottom bar.** `MochiBottomNav` (`widgets/bottom_nav.dart`) is the sidebar's job on a phone, so it takes the same kind of list and leaves the page to the app. Destinations share the width with `Expanded` and the chosen one carries a soft pill behind its icon, which the hover and press layers then sit on top of. It adds `MediaQuery.paddingOf(context).bottom` itself, since it runs to the bottom of the screen. Its row is *not* stretched: the bar sits at the bottom of a column with an unbounded height, and a stretch would hand that infinity to the destinations. On a raised theme it is `floating` by default (`MochiBottomNavVariant`, which `variant:` overrides either way): clear of the screen's edges and over the home indicator rather than on it, `radius.xl` rather than full — a pill would be the one fully round thing in a kit whose corners are steps of a scale — and no wider than `maxFloatingWidth` (480), since on a tablet a bar the width of the screen is a strip with a few icons lost in it. Each destination there is a block of its own, `radius.lg`, set in from the bar by exactly `xl − lg` so the chosen one's curve runs alongside the bar's whatever corners the theme has; docked, the fill stays a small block behind the icon at `radius.sm` — it is little taller than the icon, and `lg` was past half its height, which drew a pill all the same. Destinations stand `space.xs2` apart in both, so a hovered one beside the chosen one reads as two blocks. It is a phone's bar: a wide screen puts the same list in a `MochiSidebar`, switched at a breakpoint, and docked is for a desktop window narrowed to a phone's layout.

**Calendar.** `MochiCalendar` (`widgets/calendar.dart`) is the body of every date picker here, with one constructor per thing it can pick — a day, a set of days, a `MochiDateRange` — because the three carry different values and folding them into one parameter would mean a dynamic or a null-check per press. The month it shows is its own unless `month` is given, the same controlled/uncontrolled rule as everything else; the keyboard walks the grid and steps into the next month when it runs off the edge, which is one move, not two. A range is drawn as one band: only its ends are rounded, so the middle reads as joined, and those two ends are filled solid while the days between them are tinted — they are the days you chose, the rest came along with them. A day picked on its own counts as both ends of itself, which is what keeps a single or multiple selection round on all four corners. A range can also be drawn in one drag, anchored on the day the finger went *down* on: by the time a drag gesture starts it has already moved the slop distance, which is a different day. That anchor is kept for the whole gesture rather than read back out of the range on each update — dragging towards earlier days makes the moving end the range's *start*, so an anchor taken from there would travel with the finger and the run would only ever be a day or two long. A test for this has to walk the drag day by day: one that lands in a single jump asks the question once, and any anchor at all answers that correctly. Six weeks are always drawn, and the month's name never wraps, so the calendar is the same size in February as in August — one that changed height would shove whatever sits under it. Month and weekday names are `MochiStrings` like every other word a component says (`months`, `weekdays` Monday-first whatever the week starts on, and `monthYear`, since English puts the year after the month and Chinese doesn't).

**Time picker.** `MochiTimeWheel` (`widgets/time_picker.dart`) is columns of numbers on `ListWheelScrollView` with `FixedExtentScrollPhysics`, drawn flat rather than as a barrel (`diameterRatio: 100`) — these are numbers to read, not a wheel to admire. One band behind all the columns marks the chosen row, rather than one mark per column, since the columns are one time between them. The hours and minutes loop (23 is one notch from 00) and the AM/PM column does not, because there is nowhere to go round to. `MochiTime` is the value type — Flutter's `TimeOfDay` lives in Material — and `MochiTimePicker` wraps the wheel in the same field and the same popover-or-sheet rule as the date picker. Two things a wheel needs that a list doesn't: putting a column where a value from outside says it belongs has to happen *after* the frame and must not report a change of its own (`didUpdateWidget` runs during a build, and a jump from there lands `onSelectedItemChanged` — and so the parent's `setState` — in the middle of one), and a mouse has to be added to the scroll behaviour's `dragDevices`, or on a desktop platform the wheel can only be turned, never dragged. A mouse notch is taken over too, one notch to one row, by *jumping* rather than animating. Three things force that shape. A scroll event carries whatever pixels the device felt like sending (50 here, 120 and accelerating there), which over 32-pixel rows is two or three at a time and a different number on every turn. The handler has to be registered from the *rows*, since a pointer signal goes to whoever registers first and the scrollable's own handler sits between the two — and on the rows it needs `HitTestBehavior.opaque`, or it is only hit while the pointer is over the glyphs. And it cannot animate: a scrollable wraps its contents in an `IgnorePointer` while a `DrivenScrollActivity` runs, so a notch arriving mid-journey never reaches the rows at all and falls through to the native pixel scrolling — which is exactly the stumble back and forth you see when turning the wheel quickly. Landing at once leaves no window for any of it.

**Date picker.** `MochiDatePicker` (`widgets/date_picker.dart`) is the calendar in something that opens: a popover under the field from tablet width up, a sheet from the bottom on a phone — the same breakpoint rule as `showMochiModal`, since what adapts is where it is shown, not what it is. `showMochiSheet`'s builder returns the `MochiSheet` itself, the way a dialog route's does. A single day closes it, because picking one is the whole errand; a range waits for its second end. The day is written through `strings.date`, which is a function for the same reason `monthYear` is: English counts up and Chinese counts down. A range writes what its two ends share only once (`strings.dateRange` with `monthsShort`, and no year at all when it is this one) — two full dates side by side don't fit a field — and the field gives a range two lines rather than an ellipsis, since a range spanning two years has nothing left to shorten and half a date says nothing.

**Accordion.** `MochiAccordion` (`widgets/accordion.dart`) owns nothing but the question of which rows are open: every row is a `MochiCollapsible`, the one way things open and close here. Single mode is one line of logic — opening a row replaces the set rather than adding to it — which is why it isn't a separate component. Two things it does add: a heading in the `title` typeface a step larger than the answer under it, since at the same size the two read as one block of text — and body at w600 is not enough on its own, Comfortaa's weights being close together (check a weight by its `wght` axis in `fontVariations`, not by the `FontWeight` beside it: the axis is what a variable font actually reads), and a margin around each row so the header's hover fill stops short of the line between rows rather than running into it.

**Avatars.** `MochiAvatar` (`widgets/avatar.dart`) falls back on its own, picture → initials → icon, and shows the fallback while the picture is still coming rather than a hole where it will be; a failed load is remembered in state, so a rebuild doesn't ask for it again. Initials are cut to two letters (one from the first word and one from the last, when there are two). `MochiAvatarGroup` overlaps them through `Overlap` (`widgets/overlap.dart`), the negative-margin render box the joined badges already used — `Padding` refuses negative insets outright — and each avatar wears a ring of the surface colour so the one under it reads as behind rather than touching.

**Sidebar.** `MochiSidebar` (`widgets/sidebar.dart`) holds two different kinds of opening and closing, and needs both: a group folding its own items away (that is `MochiCollapsible`), and the whole column narrowing to a rail of icons. The rail is a width through `MochiValueTransition`, published to the rows as a 0-to-1 `open` through a private scope, so the column moves as one piece. A label is clipped by an `Align(widthFactor: open)` and faded with it rather than removed: the icon then keeps its place instead of jumping as the text goes, and the row survives the trip. The row keeps one shape the whole way — the icon, then the label's slot — and the icon walks there on a leading padding that eases from the row's start to the middle of *the rail*, a width the sidebar works out once and publishes. Two ways that go wrong: swapping in a centred icon at the last pixel makes it jump, and centring it in the row it is currently in sends it out to the right and back, because that middle is sliding left underneath it. Below half open a row wears its label as a `MochiTooltip` (taken from a `Text` label when no `tooltip` is given) and a group folds its whole heading away — chevron included, through `MochiCollapsible.headerVisibility`, since a lone chevron over a group with no name left says nothing about what it would fold — rather than dropping it — a heading over icons says nothing, but taking it out in one frame makes the column's height jump while its width is still gliding. A collapsible group is also forced open on a rail: the heading that folds it is gone, so hiding its items would leave no way back to them, and its header is `enabled: false` down there, since nothing with no height should be a press or a tab stop. A `MochiSidebarHeading`'s `trailing` (the collapse button) is what a rail keeps instead of the name: one thing fits, and that is the one that gets the sidebar back. Whether it is a rail is a `MochiControl<bool>` named after that state, `collapsed:`: `.managed()` by default, so a sidebar collapses with nothing said; `.lifted` for an app that saves it; and an explicit `collapsed: null` keeps it at its full width with no button. A sidebar in a `MochiScaffold`'s drawer is held at its full width too, whatever it was given — the drawer wraps its content in a private `FixedSidebar` (`widgets/fixed_sidebar.dart`), since a rail there would only be a thinner drawer. Where it can collapse, a heading with no `trailing` of its own carries that button by itself (`automaticTrailing`, the icons `sidebarCollapse` / `sidebarExpand`, the words `collapse` / `expand`), the same way a header puts in its drawer button. The `footer` is a list, inset and spaced exactly as the items are: outside that padding a row ran into the sidebar's edge, where a window's rounded corner cut it, and on a rail its icon aimed at a middle computed for the padded rows and stopped 4px short of it.

**Controls.** A widget that can work either way — its state held by the app or by itself — takes a `MochiControl<T>` (`widgets/control.dart`), forui's pattern and names, in a parameter named after the state it holds rather than a generic `control:` (`collapsed:` on a sidebar, `expanded:` on a collapsible), so the call says what is being controlled: `.lifted(value:, onChanged:)` is the app's (it rebuilds the widget with the new value; `onChanged` only asks), `.managed(initial:, onChanged:)` the widget's own. One sealed type rather than `value` / `initialValue` / `onChanged` side by side, so which one holds the state is written down where it is chosen, and passing both is not something that compiles. A widget whose value is always the app's — a switch, a select, a slider — keeps a plain `value` and `onChanged`, as Flutter's own do: wrapping that in a control would say nothing more at greater length. Inside, a `State` holds a private `ControlledValue<T>`: `value(control)` to read, `change(control, next, setState)` to move a managed value and report either, and `update(old, control)` in `didUpdateWidget`, so a control handed back from lifted to managed keeps the app's last value rather than snapping back to where it started. The text fields keep their `controller` for now.

**Segments and tabs.** `MochiSegmentedControl` (`widgets/segmented_control.dart`) is one row of choices, and tabs are an `appearance` of it (`underline`) rather than a component of their own — what changes is whether it reads as a control or as the tabs over a page; switching the content below stays the app's own `switch`. The slide has its own motion token (`motion.indicatorDuration` / `indicatorCurve`), and it is linear rather than eased: the marker is going from one segment to the next because a press told it to, and easing either end of so short a trip reads as hesitation. Segments share the width equally, so the chosen one never shuffles its neighbours, and the indicator behind them is an `Align` whose `AlignmentDirectional.x` walks from -1 to 1 through a `MochiValueTransition` over a `FractionallySizedBox(widthFactor: 1 / count)` — no `LayoutBuilder`, which would refuse to answer the intrinsic-width question `expanded: false` asks (a flex row's intrinsic width is its widest child times the number of them, which is exactly equal segments). Only the indicator is rebuilt as it slides, not every segment: an animation that rebuilt the whole control on every tick costs enough on a busy page to lose the frames the slide is made of. A segment's label is `Flexible` and ellipsized, since segments share the width equally and a long one would otherwise run over its neighbour. Segments sit inside `ExcludeFocus`: the control is the tab stop and the arrows move the choice, walking past any segment that is disabled. `assert(children.isNotEmpty)` lives in `build`, not the constructor, because a const list's length can't be read at compile time.

**Slider.** `MochiSlider` (`widgets/slider.dart`) keeps the last value it sent until the parent rebuilds with it, the same trick as the stepper: a drag moves faster than frames arrive. The thumb's centre travels `width - thumb`, so it never hangs off either end, and the pointer is mapped through that same travel. In right-to-left the track is mirrored and the arrows keep moving the thumb the way they point, so left is more. It grows while held rather than shrinking, like a button. The band it answers the pointer in is 28 tall (44 on touch) whatever the size, since a line and a small knob are almost nothing to aim at — and a press that misses inside a scrolling page scrolls the page instead. `MochiSliderMetrics` (thumb 12 / 16 / 20 / 24 on the desktop scale) goes through `MochiValueTransition`. A `Semantics(slider: true)` needs `increasedValue`/`decreasedValue` whenever it carries `onIncrease`/`onDecrease` — the framework asserts on one without the other.

**Searching.** `MochiSearchBar` (`widgets/search_bar.dart`) is a `MochiTextField` with the magnifier, the × and a debounce. Two callbacks, because they answer different questions: `onChanged` is every keystroke (what the field says), `onSearch` is the query worth running (after the typing stops, or at once on submit or on a clear — waiting to show everything again only reads as slow). It remembers the last query it dispatched, so a submit after the timer has already fired doesn't search twice, and a query typed and taken back inside the debounce never runs at all. `loading` swaps the × for a spinner in the same place rather than adding one beside it. Suggestions are not part of it: that is `MochiAutocomplete` with a magnifier as its prefix.

**One-time codes.** `MochiOtpField` (`widgets/otp_field.dart`) is one `EditableText` holding the whole code, hidden in a 1×1 box behind a row of drawn boxes — not a field per box, which would have to split a paste by hand and chase the focus about. The caret can only be at the end (a listener puts the selection back there), so a character always lands in the next empty box and backspace always takes the last one out; the platform's `oneTimeCode` autofill fills it like any other field. The boxes take the pointer and hand focus to the hidden field, which has `rendererIgnoresPointer` and no selection, handles or context menu of its own. The box being filled paints its own caret, a blinking bar that stops under `MediaQuery.disableAnimations`.

**Autocomplete.** `MochiAutocomplete` (`widgets/autocomplete.dart`) wraps the widgets layer's `RawAutocomplete`, which mounts the list through `OverlayPortal.overlayChildLayoutBuilder` and hands it the field's width and the room below, so the panel only has to fill what it is given (a `SizedBox(width: double.infinity)` inside the height cap). Unlike a select, the text is what counts: anything can be typed, `onChanged` reports every keystroke and `onSelected` only fires for an option. The frame is *outside* the `RawAutocomplete`, so the list hangs from the box rather than from below a description — which is also why there is no `maxLength`, whose counter would sit between the two. The rows are `MochiMenuItem`s with no focus of their own (`RawAutocomplete` keeps the panel out of traversal): the arrows move a highlight index, read through `AutocompleteHighlightedOption.of`, and the highlighted row is marked `selected`; a `GlobalKey` per row lets the panel `Scrollable.ensureVisible` it as the arrows walk past the end.

**Tooltip.** `MochiTooltip` (`widgets/tooltip.dart`) wraps Flutter's widgets-layer `RawTooltip`, adding a theme-styled bubble (inverse `neutral` tone), a `positionDelegate` that places it above/below the child instead of over its center, and keyboard-focus support (RawTooltip has none). `MochiButton(tooltip:)` is a shorthand. On touch, a descendant `onLongPress` wins the gesture arena over the tooltip's long-press trigger.

**Scrollbars.** `MochiScrollBehavior` installs `MochiScrollbar` on desktop platforms: a rounded thumb, always visible, thickening from 6 to 11 once the pointer comes within 32px of it and for the whole of a drag (tracked through a global pointer route, since the release can happen anywhere). Its `Listener` is `translucent`: the `MouseRegion` under it is not opaque, so deferring to the child would keep it out of the hit-test path. Containers that scroll (`MochiCard`, `MochiTileGroup`) clip their content so the thumb stays inside the rounded corners. That clip goes *outside* the padding, at the card's own outline: inside it, the card's radius rounds the **content's** corners instead and bites a piece out of anything sitting in one — a date in the top left of a tile, say. The padding then adds the decoration's own (the border's width), the way `Container` does, so content sits inside the line rather than under it.

**Wheel containment.** `MochiScrollArea(containScroll: true)` (the default) keeps a mouse wheel over the area from scrolling the page behind once the area hits its end. A wheel event goes to the first scrollable on the hit path that registers with `GestureBinding.pointerSignalResolver`, and a `Scrollable` only registers while it can still move; so at the end the area registers a do-nothing handler ahead of whatever lies further out. It does so only while its content overflows, and only along its own axis, so an area that fits never blocks the page. Its `Listener` has to be `translucent`: on desktop the scrollbar wraps the list in a `MouseRegion(opaque: false)`, and a non-opaque `RenderMouseRegion` reports "not hit" to its parent even when its child was, so a `deferToChild` ancestor silently drops out of the hit path. The Android-default tests missed this; the regression test runs under `TargetPlatformVariant.only(TargetPlatform.linux)`. Test desktop-only chrome on a desktop platform. Touch and trackpad drags don't chain in the first place: the inner scrollable wins the whole gesture.

**Bounded constraints.** `MochiDivider` and `MochiLinearProgress` expand along their axis and need a bounded parent. A `CustomPaint` with no child is the mirror image: its preferred size is `Size.zero`, so a loose constraint collapses it and it paints nothing at all. Watch for widgets that silently shrink instead: a `FractionallySizedBox` under loose constraints sizes to its child, which once pinned the indeterminate progress bar in place. When something "doesn't animate", check the on-screen geometry (log `RenderBox.localToGlobal`) before trusting a screenshot — X11 captures of the GL window and the browser pane can both be stale.

**Sizes.** One `MochiSize` enum (`xs, sm, md, lg`) is the size axis of every component that has one; what each step measures lives in that component's `XxxMetrics` (`MochiButtonMetrics`, `MochiCloseButtonMetrics`, `MochiBadgeMetrics`, and `MochiProgressMetrics`, which the ring and the bar share so a size means the same weight for both), which needs value equality to go through `MochiValueTransition`. A badge defaults to `sm`, a step under a control, since it sits beside text.

**Joined groups.** `MochiBadgeGroup` follows the `MochiTileGroup` pattern: an InheritedWidget tells each child its place (only / start / middle / end), and the child squares off its own inner corners with a `BorderRadiusDirectional`. Neighbouring borders are shared by pulling each later badge back over the previous one by the border width (`Overlap` in `widgets/overlap.dart` — a negative margin, which neither `Padding` nor `Row.spacing` allows; the avatar group stacks with the same box), mirrored for right-to-left. In tests, a `Directionality` placed *around* `MochiApp` is overridden by the one `WidgetsApp` installs; put it inside `home`.

**Cards.** `MochiCard` is a surface for grouped content, and two things it now carries are worth saying. First, though: `appearance` is `MochiCardAppearance` (`elevated`, `outlined`, `soft`), not the button's appearances — a card holds controls tuned for the page and the surface, so a solid fill leaves them unreadable, and one with neither fill nor border is not a card. Only `elevated` casts a shadow, since a shadow under a see-through card shows through it; `outlined` fills with transparent *surface* so its tints land on whatever it sits on; `soft` fills with its intent's `soft`, which is the one case where `intent` colours an unselected card. `selected` (with `intent`) is a card that has been picked — one of several in a multi-select — drawn the way every other chosen thing in the kit is: the intent on the border and the tone's soft fill mixed over the *card's own ground* with `softOn`, which is exactly what a chosen `MochiRadio(appearance: .card)` takes, so the two read as the same kind of picked. And `title` / `titlePrefix` / `titleSuffix` put a heading over the content in the `title` typeface — a heading, not body at a heavier weight, which is the rule an app composing the row itself gets wrong first. `titleGap` sets the room between that row and the content (`space.sm` by default, taken as given rather than scaled by density). A titled card that has been *given* a height (tight, or stretched under `IntrinsicHeight`) hands the content the height left under the title, so a `Center` there centres in the card; a merely bounded one keeps its content's own height, or a centred child would stretch it to the screen. `MochiCard.collapsible` is the same row with the folding; the plain one has no divider under it, since nothing is pressable there for a hover fill to run into. The row is an `xs` button tall whether or not it holds one, and it says so: a private `ActionScale` (`widgets/action_scale.dart`, not exported) publishes that size, and a `MochiActionBar` with no `size` of its own takes it, so `titleSuffix: MochiActionBar([...])` costs no height and nobody has to know the number. Anything passed explicitly still wins. A row the height of a line of text would have had to shrink the button to a speck instead, which is what `dense` is for when the line really cannot grow.

**Collapsing.** `MochiCollapsible` (`widgets/collapsible.dart`) is the one way things open and close under a header — `MochiCard.collapsible` now, an accordion and sidebar groups later. The body grows with `Align(heightFactor:)` inside a `ClipRect` over `motion.sizeDuration` / `sizeCurve`. Whether it is open is a `MochiControl<bool>`, `expanded:`: `.managed(initial:)` by default, or `.lifted`, where a press only calls `onChanged` and the widget follows what it is rebuilt with (that is how an accordion keeps one open). `MochiCard.collapsible` and `MochiSidebarGroup` take the same `expanded:` and hand it down; a group on a rail swaps in a lifted `true`, since the heading that folds it is gone. With `maintainState`, the body keeps the *same* widget tree open and closed (an `Offstage` that toggles, not a different parent), otherwise its state is lost on the swap; a closing body is wrapped in `ExcludeFocus`. That body is `RevealBody` (`widgets/reveal.dart`, not exported), and `MochiReveal(expanded:)` is the same body with no header and its own controller: for content opened by something elsewhere — a switch, a choice — where a collapsible with its chevron hidden would still be a pressable row that doesn't look like one. The header tints rather than grows, and its focus ring is `inset` because whatever holds it (a card) clips. Its bottom corners are squared off only when it has a `divider`: that is the line the body meets it along, and without one a straight edge in mid-air reads as a seam that isn't there. A collapsible card moves its padding inside, so the title row's hover fill reaches the card's edges, and puts a `divider` under the title row with the body fully padded below it: letting the row's bottom padding stand in for the gap looks right at rest but, once hovered, the fill runs straight into the content.

Each one: theme reads in the innermost widget, colors via `MochiStateTransition`, shapes via `geometry.shape` and `MochiClip`, sizes from `theme.touch`, and `MediaQuery.disableAnimations` honored by anything that animates on its own. Verify new components in the real app in **debug** mode (`fvm flutter run -d linux`): profile builds have assertions off, so unbounded-constraint mistakes render as silently missing widgets instead of errors.

**Pickers.** `MochiDatePicker`, `MochiTimePicker` and `MochiDateTimePicker` are one field with three things behind it. The box itself is `PickerField` (`widgets/picker_field.dart`, not exported): a text field's look with an icon at its end, which is why a date, a time and a name line up in one form. Where the panel opens comes from the breakpoint the modals use — a popover from tablet width up, a sheet on a phone — and the two are answered differently on purpose. A popover is glanced at and dismissed, so it reports every press as it happens and closes once there is nothing left to pick (a day, or a range's second end); the date-and-time picker closes for neither, so its popover carries an OK button. A sheet covers the page, so it is confirmed: `showPickerSheet` (`widgets/picker_sheet.dart`) holds the draft itself, the panel is drawn from that draft, and only the button hands it back — dragging the sheet away or pressing the barrier drops it, and the button is disabled while the draft is not an answer yet (no day at all, half a range). That draft is not a matter of taste: **a sheet is a route, and a route builds its page once**, so a picker's own `setState` never reaches inside it — a calendar pushed in there went on showing the day it was pushed with, and a range could never be given its second end. The sheet also raises the default half-screen cap to 0.9, scrolls its panel, and keeps the button outside that scroll view, since what keeps the answer should not be what a short screen pushes out of sight.

**Picking a colour.** `MochiColorPicker` (`widgets/color_picker.dart`) is the shade square, a hue bar, an optional opacity bar, a hex field and a row of swatches; `showMochiColorPicker` is that in a modal — a dialog from tablet width up, a sheet on a phone, with a draft that only leaves through the button, the same bargain the date pickers' sheets make (and the button cannot be a `MochiModalAction`, whose value is fixed when it is built, which a draft is exactly not). What the picker keeps while it is open is an `HSVColor` rather than the `Color` it reports: black is every hue at once, so a picker holding only the colour forgets which hue it was on the moment a drag reaches the bottom of the square, and the thumb springs back to red — the guard in `didUpdateWidget` is what tells a colour the parent handed back from one that really came from outside. The square answers `onHorizontalDrag*` and `onVerticalDrag*` rather than a pan: a modal's body scrolls, and a pan's slop is twice a drag's, so the scroll view claims the gesture several moves before a pan would ever accept it and the square would scroll the dialog instead of picking a colour. A test for that needs both a screen short enough for the body to really scroll (a scroll view whose content fits refuses drags outright, so nothing contests the gesture) and a drag made of small steps (one long jump crosses both slops in the same event, where the inner recognizer wins whatever kind it is) — without either, the test passes against a pan. The chequerboard under a see-through colour, the gradients over it and the superellipse that clips them are one `CustomPainter` (`_ShapePainter`), since the pattern has to stop exactly where the gradient does — and the square's two gradients go through the same painter rather than two stacked `ShapeDecoration`s, which antialias one edge twice and harden it into a line around the square. Watch the painter's own size there: a `CustomPaint` with no child asks for `Size.zero`, so the bar's track has to be given a width outright, or the loose one it is handed collapses it and the knob is left standing on nothing. The hex is `AARRGGBB` with opacity on and `RRGGBB` without — the order `Color(0xFF7C3AED)` is written in — six digits keep whatever opacity is already set, half a hex does nothing at all, and leaving the field puts the colour back in it. Swatches default to the theme's own six intents, with the tick drawn in whichever of the page's inks reads on the swatch (`readableOn`'s neighbour, `mostReadable`); pressing one changes the colour and leaves the opacity where it was put. `showMochiColorPicker(defaultColor:)` adds the colour the app would have used anyway as one press, under the picker rather than among the actions: going back to the default is not an answer — it changes the draft and leaves the modal standing, and on a phone the actions are a stack of full-width buttons where it would read as a third way out. It greys out once the draft is already that colour, and its words come from `strings.reset` unless the app passes its own. On a phone the whole thing goes in a sheet, which is as tall as the picker: one that had to be scrolled through would be one whose square you cannot drag in, since the same gesture would move the sheet's own scroll view. The picker itself has no such parameter: what the default is belongs to the app, and a page that shows the picker inline can put its own button beside it. The bars and the square are each a tab stop with arrow keys, since a colour that can only be dragged to cannot be reached from a keyboard at all.

**Split panes.** `MochiResizable` (`widgets/resizable.dart`) keeps its sizes as fractions of the whole, not pixels, so resizing the window keeps the split instead of handing every new pixel to one pane; the handles are taken out of the total first, so a pane's share means the same whatever a handle measures. A drag moves one boundary only — the pane before it gets exactly what the pane after it gives up — and what stops it is whichever of the two runs out of room first (`lower`/`upper` from both panes' `minSize`/`maxSize`, computed together, since clamping to one side at a time can leave the other short). Each handle is its own tab stop with arrow keys, because a split that can only be set by dragging cannot be set at all without a mouse, and its focus ring is `inset` since there is nothing outside a line between two panes to paint on. Splits nest: a pane's child can be another `MochiResizable` on the other axis.

**Pull to refresh.** `MochiRefresh` (`widgets/refresh.dart`) wraps a scrollable and reads its notifications: `OverscrollNotification` is what a clamping physics reports when the finger keeps pulling at the top, and a bouncing one instead moves the list past its own end, which comes through as a `ScrollUpdateNotification` with `pixels < minScrollExtent` — both are handled, since the physics is the platform's business. The pull is halved on the way to the indicator, which is what makes the gesture feel like it is against something, and the extent lives in a `ValueNotifier` so a drag doesn't rebuild the list under it. The indicator is the kit's own `MochiCircularProgress`: determinate while the finger is deciding (the ring is how much pull is left), indeterminate once the errand is running, because how long it takes is nobody's to say. The list is held down until the future completes however it ends, and a failure goes through `FlutterError.reportError` rather than being swallowed or left on a future nobody holds. A mouse gets to pull it as well (`mouseDrags`, on by default): on a desktop platform a scrollable refuses a mouse drag unless it is told otherwise, and a wheel at the top of a list reports no overscroll at all, so without that there is no gesture there to make. It is deliberately not part of the toaster — see the toast notes for why.

**Swiping.** `MochiSwipeActions` (`widgets/swipe_actions.dart`) slides a row aside to show `MochiAction`s behind it — `leading` and `trailing`, following the text direction — the same value type a bar of actions is made of, so the label is each action's name in semantics too and a screen reader is offered them as custom actions with no swipe at all. Menus are skipped: there is no room behind a row to open one. The offset is an unbounded `AnimationController` in pixels, positive to the right whatever the direction, and the actions behind it are laid out in an LTR row reversed for right-to-left, so "outermost" (the last trailing, the first leading) is always the one at the screen's edge. Past half its actions a row stays open, short of that it springs back, and a fling decides by its direction; past its actions the drag is halved, unless `fullSwipe` (off by default — it is also the easiest way to delete by accident) lets it run across and fire the outermost action past six tenths. Which one that is has to show before the release: up to their own width the buttons share what is revealed, past it the extra all goes to the outermost, and once the drag is past the line a second controller (`_takeover`, eased over `stateDuration`) gives it the whole width, handing it back if the drag returns — two buttons widening side by side said nothing about which would run. One row is open at a time (a private registry, like the popovers'), pressing an open row only closes it (`AbsorbPointer` under a tap that settles), and a scroll of the list it is in closes it through the `Scrollable`'s position. Dragging follows `theme.touch`: a mouse has no swipe, so on a desktop the same actions belong in a `MochiContextMenu`. A test drags from the row's middle rather than its text: once open, the text has slid under the clip and a gesture started there hits nothing.

**Sorting.** `MochiSortable` (`widgets/sortable.dart`) wraps the widgets layer's `ReorderableList` and adds the two things a kit has an opinion about: what starts a drag, and what a carried row looks like. With a mouse that is `MochiSortableHandle` — a row you can drag by its middle is a row you cannot select text in or press a button on by mistake — and on touch it is a long press anywhere on the row, since a finger has no aim for a small grip; the default follows `theme.touch`. It passes `onReorderItem`, not the deprecated `onReorder`, so the index a row lands at is already counted with that row taken out and nobody writes the `if (newIndex > oldIndex) newIndex -= 1` adjustment by hand. Row keys go on the outside (a `KeyedSubtree`) with the spacing inside, so the gap travels with the row and a dropped row lands where the eye put it. The carried row grows slightly and takes an `lg` shadow, both driven by the drag's own animation; that shadow is cast off a superellipse (`liftRadius`, a card's corners by default), since a rectangle's shadow behind a rounded row shows up as a grey box with corners nobody drew. It is also painted *behind* the row and inset by the spacing, because the row the list hands the decorator already has the gap inside it: cast around that padded box, the shadow stands proud of the row on every side and flashes above it as the row is picked up.

**Skeletons.** `MochiSkeleton` (`widgets/skeleton.dart`) is a block, a circle or a run of text bars, and the shimmer over it is one moving gradient behind a `ShaderMask` rather than a stack of fading layers. Every skeleton on a page is in step: the controller starts at a phase taken from `SchedulerBinding.currentSystemFrameTimeStamp`, not at zero, or a list of rows waiting for one thing shimmers in a dozen phases and reads as noise. That clock rather than `DateTime.now()` also means a test can see it, since fake time moves the scheduler's and not the wall's. It repeats forever, so **`pumpAndSettle` never returns in a test with one on screen** — pump frame by frame, or turn animations off, which is also what `MediaQuery.disableAnimations` does to it. A bar with no width of its own fills the line like a divider, so a paragraph of them needs a parent with a width.

**The preview gallery.** `lib/main.dart` is the shell — a sidebar of pages, a top bar, and a list of sections — and the samples live in `lib/gallery/*.dart` as `part` files, so they stay private to the one library and nothing had to be renamed when they were split out of a single 3,500-line file. The top bar carries what applies to everything (theme mode, touch, language, corners, density, text scale, brand colour), a **viewport** switch that sets both a width and a `ResponsiveScope` tier (so a picker's popover-or-sheet decision can be seen without resizing the window), and the page's own **knobs** (size / intent / enabled), which a page declares and the samples read through a private `_Knobs` inherited widget. Each knobbed page opens with a "knobs" section showing those values applied; the rest of the samples keep their own deliberate variations, since a matrix of every intent × appearance × state is the thing the gallery has that a component catalogue does not. Samples lay out in `Wrap`, not `Row`: the body is narrower than the window now and narrower again in a phone viewport, and a `Row` of fixed-width samples simply runs off it. `test/gallery_smoke_test.dart` opens every page at every viewport and walks the render tree for a `RenderFlex` whose children outgrow it, which is the cheapest check that no component throws or runs off a narrow page — it is where the segmented control's unellipsized label, the menubar's fixed row and the pagination's fixed window all turned up.

**Scaffold.** `MochiScaffold` is a column — header, padded content, footer — until `extendBody` lays the content over the whole page with the bars standing over it, so a list scrolls on behind them. The bars are *measured*, not declared: a private `MultiChildLayoutDelegate` lays them out first and hands their heights to the body inside its constraints (a `BoxConstraints` subclass carrying `top` and `bottom`, read by a `LayoutBuilder`), which is how the number gets from layout to build without a frame's delay — and why `MochiHeader` is not a `PreferredSizeWidget`: a header that grows with `touch`, `density` and `textScale` could only declare the wrong height. The body gets them as `MediaQuery.padding` (a side with no bar keeps the system's inset), which a `ListView` or `GridView` reads by itself; the vertical page padding goes into that inset rather than around the content, or it would hold the list back from the bars. The bars are given a tight width and an *unbounded* height, as the column gave them: a header centres its title with an `Align`, and under a bounded height it filled the page. The safe area keeps only the sides, since the bars clear the top and bottom insets inside their own fill — `MochiHeader` pads by `MediaQuery.paddingOf(context).top`, which a plain scaffold's `SafeArea` has already zeroed, and a floating one takes it as margin. A `plain` header has no fill, so content shows through it: pair `extendBody` with `bordered` or `floating`. A body that scrolls takes `padding: EdgeInsets.zero` and puts `pagePadding` inside the scroll view instead: padded from outside, the view stops short of the page's edge, so rows are cut off in mid-air and a raised card's shadow is clipped at the sides — and `extendBody` only moves the *vertical* padding into the inset, so the sides need it there too. The scaffold cannot decide this itself, since it cannot tell a list from a column. `headerOverlay` is drawn over the header (after the sidebar, so it slides in across it, and under the drawer): the content's width, at least the header's height and as tall beyond that as it likes. It exists because something covering the header — a selection bar — has to follow the sidebar as it slides, narrows to a rail or goes, and only the layout delegate knows where that edge is; placed in a `Stack` around the scaffold it needs the sidebar's width written in, and placed in the header's own `Stack` everything past the header's box takes no presses. Only its own box is hit, so the header and the page stay live around it. The scaffold slides it in from the screen's leading edge and out again when it turns null — positioned by the layout delegate over the whole distance, since a slide by its own width ends at the sidebar's edge, where a card drawn over the sidebar is seen to stop and vanish — keeping the last one on the tree (letting presses through) until it has gone; while it arrives it absorbs them, so a press lands neither on a card half in place nor on the header button it hides, since an app cannot hold on to a widget it has already taken away; one the page is built with is simply there.

**Navigation by width.** A `MochiScaffold` with a `sidebar` swaps it for its `footer` at `sidebarFrom` (tablet by default): the sidebar stands beside the content from there up, and below it the footer shows and a `drawer` can be pulled out over the page. Without a sidebar nothing swaps — the footer shows and the drawer opens at every width. The three are separate slots on purpose: what a phone's drawer holds is rarely what a desktop's sidebar does, and with one slot per place the app writes each one's contents and never asks for the width itself. Crossing the breakpoint runs one controller from 0 to 1 that the layout delegate listens to (`relayout:`), so the sidebar slides in from off the edge, the footer slides down out of sight and the page narrows, all laid out again per tick and never rebuilt; every slot stays on the tree whichever is showing — a hidden one is `ExcludeFocus` + `IgnorePointer` at once and `Offstage` only once it has finished leaving — so the page keeps its state (a half-typed field) across the swap. The drawer is *not* a route, for the same reason a picker's sheet keeps a draft: a route builds its page once, and a drawer pushed as one would go on showing the session that was chosen when it opened. It is a layer in the scaffold's own `Stack`: a dimmed page that closes it, the panel at most 320 wide or 85% of the screen, Escape, a focus scope that hands the focus back on close, and a drag that drives it either way. The strip along the leading edge that pulls it out is always on the tree, *under* the dimmed page — a strip that left the tree once the drawer counted as showing ended the drag it had just started — and only listens on a page with nothing to go back to, since a pushed page's edge is its back drag; it is widened past `MediaQuery.systemGestureInsets`, which Android keeps for its own back gesture. `MochiScaffold.of(context)` is the state, as Material's is: `openDrawer`, `closeDrawer`, `isDrawerOpen`, `hasDrawer` (false beside a sidebar, where `openDrawer` does nothing rather than throw, since a width can change under a button). A `MochiHeader` with no prefixes puts the button that opens it in front of its title whenever there is a drawer to open (`automaticPrefix`), so the button comes and goes with the width without the app following it.

**Large titles.** `MochiLargeTitle` (`widgets/large_title.dart`) is a page's title written large (`title.xl3`) as the first thing in its content, and the header's own title fades in as it scrolls away — over the last half of it going under the header's bottom edge. It is content, not header: nothing collapses, so the header keeps one height and the list one padding, and no sliver or `CustomScrollView` is needed. It reports to the scaffold how much of it is covered (`MochiScaffoldState.largeTitleCovered`, measured against the header's box, which the scaffold keeps a key on), and only the header's title listens, so a scroll rebuilds nothing but that one `Opacity`. Two things about measuring it. A scroll is heard *before* the frame lays the list out again, so reading the box in the listener gives where it was; it keeps where it was last laid out and the scroll's pixels then, and moves that by the scroll's own distance. And it never writes the notifier while the tree is being built or torn down — leaving, or moving to another scaffold, clears it in a post-frame callback, and only if it is still the one that wrote last (`largeTitleOwner`), since the next page's may already have spoken. Outside a scaffold it is only a heading.

**Responsive.** `theme/responsive.dart` defines `MochiBreakpoint` (content width + 24px gutters: 768 / 1008 / 1248, plus 1600 for fullhd) and `MochiScreenSize`. `ResponsiveScope` can override the size; otherwise it's derived from `MediaQuery` width. Use `context.responsive(mobile: ..., desktop: ...)` for values or the `Responsive` widget for builders — both fall back to the nearest smaller tier.
