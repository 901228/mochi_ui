# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Mochi UI: a custom Flutter UI kit built on `package:flutter/widgets.dart` only — **no Material or Cupertino** (`uses-material-design: false`). Every widget, theme, and interaction state is implemented from primitives. Dependencies: `tabler_icons_plus` (icons).

Status: early WIP. Public API is exported from `lib/mochi_ui.dart`. `lib/main.dart` is a preview gallery (every button intent × appearance × state, with a light/dark/system toggle), not a real app.

Design references: Bulma for component API (intents, appearances, breakpoint names), Catppuccin Latte/Mocha for colors, forui for typography scale and button/tappable API naming. Icons: Tabler (`tabler_icons_plus`). Corners are always superellipses (`RoundedSuperellipseBorder` via `ShapeDecoration`), never `BoxDecoration.borderRadius`. Press feedback grows (iOS style), never shrinks.

## Architecture

Split into `lib/mochi_ui/theme/` (data) and `lib/mochi_ui/widgets/` (UI).

Component roadmap and priorities: `ROADMAP.md` (tick items off as they land).

**Theme access.** `MochiThemeScope` (InheritedWidget) holds a `MochiTheme` (`colors`, `typography`, `touch`, extensions; value equality); read it via the `BuildContext` extensions `context.theme` / `context.colors` (`theme/theme.dart`). `MochiApp` / `MochiApp.router` take a `MochiThemeMode`, optional `lightTheme`/`darkTheme`, and `touch` (defaults to `MochiTheme.defaultTouch` by platform), and wrap content in `AnimatedMochiTheme` → `ColoredBox(background)` → `DefaultTextStyle` → `IconTheme` → `ScrollConfiguration`, so descendants get theme-derived text, icon, and scrollbar defaults.

**Colors (three layers).**
1. `theme/palette.dart`: raw hex values (`LattePalette`, `MochaPalette`). Not exported; only `colors.dart` may use it. Some Latte accents are darkened so text reaches WCAG AA 4.5:1 — re-check contrast when changing them.
2. `theme/colors.dart` `MochiColors`: semantic tokens. Neutrals (`background`, `surface`, `overlay`, `border`, `foreground`, `mutedForeground`) plus one `MochiTone` per `MochiIntent` (`neutral, primary, info, success, warning, danger`), looked up via `colors.of(intent)`. `MochiColors.light` / `.dark`.
3. Component styles derive everything from tokens. A `MochiTone` (`theme/tone.dart`) has `base` (fills/borders), `onBase` (text on base), `soft` (tinted bg), `onSoft` (intent text on soft or page bg). Hover/pressed colors are never stored; use `MochiColors.stateLayer(base, on, states)`.

**Typography.** `MochiTypography` has two `MochiTypeface`s, `title` (w700) and `body` (w400), each with a Tailwind-based scale `xs3, xs2, xs, sm, md, lg, xl, xl2 … xl8` (`md` = 16px) and `scale(factor)`. Styles carry no color. Family is Comfortaa (variable font, wght 300–700) with FakePearl (假粉圓) as CJK fallback; both are bundled in `assets/fonts/` (OFL) and declared in `pubspec.yaml`. Change weight with `style.withWeight(FontWeight.wX)`, which sets `fontWeight` and the `wght` variation together.

**Geometry.** `MochiTheme.geometry` (`MochiGeometry`): `radius` (xs 6 / sm 8 / md 10 / lg 14 / xl 20 / full), `space` (xs3 2 … xl3 64), `shadows` (sm/md/lg layers, colored by `colors.shadow` via `shadows.of(elevation, color)`), `borderWidth`, `focusRingWidth`/`focusRingGap`, `pagePadding`. Components take sizes, radii and shadows from here rather than literals. Size-dependent metrics reference tokens through functions (e.g. `MochiButtonMetrics.radius` is `BorderRadius Function(MochiRadius)`).

**Flutter channel: master (pinned in `.fvmrc`).** Stable 3.47.x renders strokes and paths on Linux without antialiasing: Impeller's SDF renderer has no `drawPath` antialiasing (flutter/flutter#185117, still open) and relies on MSAA, which the Linux embedder did not enable until PR #191379 (flutter/flutter#191171), merged to master 2026-08-23 and **not in stable**. On master everything renders smoothly, so the project follows master and the workarounds that existed for this (a custom fill+clear superellipse border, a sweep-gradient spinner) were removed. If the project ever moves back to a stable without that fix, expect stair steps on any stroked or path-based shape.

**Antialiasing.** Never stroke a shape with the same color as its fill: the antialiased edge is painted twice and hardens into stair steps. Filled button appearances therefore keep a fully transparent `BorderSide` (which also keeps the 1px layout).

**Soft fills on surfaces.** `MochiTone.soft` is mixed over the *page background*. A selected row inside a card sits on `colors.surface` instead, where that fill is too dark to read: use `colors.softOn(tone, background)` there. The dark theme carries more accent (`softAlpha` 0.26 vs 0.14) because pastel accents wash out over a dark ground.

**Opaque row backgrounds.** A row inside a clipped, bordered container paints over that container's border. Fading the whole row (disabled rows, for instance) lets the border show through and reads as an extra outline around that one row: dim the row's content, never its background.

**Icons.** Components only draw the icons in `MochiTheme.icons` (`MochiIcons`); anything else comes from the app. Adding an icon to a component means adding a token, not importing an icon set.

**Strings.** Same rule for words: components only say what is in `MochiTheme.strings` (`MochiStrings`: `ok`, `cancel`, `back`, `close`, `dismiss`, `remove`, `search`, and a text field's `cut`, `copy`, `paste`, `selectAll`), and labels an app passes in are its own. It is a theme token rather than a `LocalizationsDelegate` — an app picks `MochiStrings.en` / `.zhHant` (or its own) for its locale and passes `MochiApp(strings:)`. A label parameter that used to default to English is now nullable and resolves at use: widgets read `context.theme.strings`; `show…` helpers and routes, which run once rather than build and may sit outside a `MochiApp`, use `MochiTheme.maybeRead(context)` and fall back to `MochiStrings.standard`. The toast's close button names itself through `Icon.semanticLabel`, not a tooltip: the toaster is above the navigator, so there is no `Overlay` for a tooltip to float in.

**Focus ring.** Use `MochiFocusRing(visible:, radius:, child:)` for every focusable component. It paints outside the child (no layout change) and always builds a `Stack`, so toggling never resets the child's state. That `Stack` uses `StackFit.passthrough`: the default loose fit would hand the child the Stack's own constraints, so anything told to fill its width (a stacked dialog action) would shrink back to its content. Because it paints outside, any clipping ancestor (scroll view, clipped card) cuts it off: reserve `MochiFocusRing.outsetOf(context)` of padding around focusable content inside clipped areas.

**Entering and leaving.** `MochiSurfaceTransition` applies the theme's `transitionDuration` / `transitionCurve` (and the quicker reverse pair) as a fade, a fade with a slight scale, or a slide. `scrim: false` drops the dimming and the travelling shadow, which a page needs (it is opaque and shares a background colour with the one it covers) but a floating surface does not: a popover paints its own shadow throughout, and a modal's dimming belongs to the barrier behind it. Pages go through `MochiPageRoute` / `MochiPage`, which read those durations from the navigator's context (the navigator asks for them before `buildPage` runs). Overlays are meant to reuse the same widget, so a dialog, a popover and a pushed page move alike.

**Motion.** `MochiTheme.motion` (`MochiMotion`) holds `stateDuration`, `themeDuration`, `sizeDuration`/`sizeCurve` (eased at both ends: a size that leaves rest at full speed reads as a jolt, since no gesture is driving it), the transition pair, and press springs. `MochiTappable(scaleOnPress: true)` wraps content in `MochiPressScale`, a render object that scales around the center while pressed (capped at `pressScale` and `pressMaxGrowth` px per side), springs back with overshoot, keeps quick taps visible for ≥90ms, snaps exactly to rest, and honors `MediaQuery.disableAnimations`. It repaints per tick without rebuilding; turn it off for list rows. It reads the theme with a fallback, so tappables work outside `MochiApp`.

**Appearance knobs.** `MochiApp(radius:, density:, textScale:)` apply to both themes. `radius` takes a `MochiRadius` preset (`sharp`, `subtle`, `standard`, `rounded`, `pill`, or `MochiRadius.scaled(f)`; `full` never scales). `density` is `MochiTheme.density`: the theme keeps the geometry it was given and exposes `theme.geometry` with the spacing and page padding already multiplied, and the metrics of buttons, close buttons, badges, tiles and menu rows multiply their heights and paddings — never text, icons, corners or lines. Because `theme.geometry` is the scaled one, never pass it back through `copyWith(geometry:)` (it would be scaled twice); change corners with `copyWith(radius:)`. `density` switches immediately in `MochiTheme.lerp` (the metrics transitions ease the sizes anyway), so it doesn't break the value-equality shortcut described under theme animation. `textScale` is not a typography scale: `MochiApp` multiplies `MediaQuery.textScaler`, so it compounds with the system's setting and reaches every `Text` below, the app's own included.

**Theme extensions.** App-specific theme data subclasses `MochiThemeExtension<T>` (implement `lerp`; add `==` if the extension is rebuilt per build) and is read with `context.theme.extension<T>()`. `copyWith(extensions:)` merges by type.

**Theme animation.** `AnimatedMochiTheme` fades the whole `MochiTheme` via `MochiTheme.lerp` (colors and extensions interpolate; typography, geometry and `touch` switch immediately). Any new field added to `MochiColors` or `MochiTone` must also be added to its `lerp` **and to its `==`/`hashCode`**: value equality all the way down is what makes `MochiTheme.lerp(from, to, 0) == to` true when a change touches none of the interpolating parts, which is how a `touch` flip is applied in one frame instead of rebuilding the whole app for 200ms to paint the same colors. Without it the measured frame rate on a busy page fell to ~12fps (build 25-75ms per frame); with it, 60fps at 4-7ms. `MochiTheme` must keep value equality for the same reason, otherwise every `MochiApp` rebuild restarts the animation. The blend is computed at `t == 0` too, so the immediately-switching fields are not held back by a frame. Under `MediaQuery.disableAnimations` it exposes the target theme directly.

**Measuring frames.** Judge motion from `SchedulerBinding.addTimingsCallback`, not from watching: log `buildDuration`, `rasterDuration` and the gap between `FramePhase.vsyncStart` timestamps. A steady 16.7ms gap is 60fps; 33.3ms means every other frame is being dropped even though each one looks affordable. Debug builds inflate build time roughly 5x, so compare like with like.

**Interaction states.** `MochiTappable` is the base for all pressable widgets. It owns a `WidgetStatesController` (hovered / focused / pressed / selected / disabled), wires gestures, keyboard activation (Enter/Space → `onPress` only), focus, cursor, and semantics, and exposes states through a `ValueWidgetBuilder<Set<WidgetState>>`. Disabled = `enabled: false`, or all of `onPress`, `onLongPress`, `onDoublePress`, `onSecondaryPress`, `onSecondaryLongPress` are null. Gesture callbacks are passed to `GestureDetector` only when non-null — in particular a registered `onDoublePress` delays `onPress` by the double-tap timeout. `selected` is owned by the widget: a `statesController` passed in gets `selected`/`disabled` overwritten from widget params. Visual widgets (e.g. `MochiButton`) build on it and resolve colors from the state set.

**Button styles.** Color intent and visual appearance are separate axes: `MochiButton(intent:, appearance:)`, where `MochiButtonAppearance` is `solid, soft, outlined, ghost, text, inverted`. `MochiButtonStyle.of(intent, appearance)` (`theme/styles/button_style.dart`) returns state-resolving color functions `(MochiColors, Set<WidgetState>) → Color`. Selected steps the appearance up one level (text/ghost/outlined → soft, soft/inverted → solid, solid → deepened); outlined keeps its border. `prefix`/`child`/`suffix` are laid out in a `Row`. Layout comes from `MochiButtonMetrics.of(size, touch:)` (heights desktop 28/32/36/40, touch 32/40/44/48); `MochiButton.icon` is square with width = height. Don't set `Container.alignment` on the surface — it makes the button fill its parent. Disabled is rendered as 40% opacity on the whole button; the focus ring is painted outside the box via a `Stack` so it never shifts layout. The border is always present (transparent when unused) for the same reason.

**State animation vs theme animation.** Inside components, don't use implicit `Animated*` widgets (`AnimatedContainer`, `AnimatedDefaultTextStyle`, …) for theme-derived values: every frame of `AnimatedMochiTheme` changes their target and restarts them. Use `MochiStateTransition` (`widgets/state_transition.dart`), which animates only when the `WidgetState` set changes and resolves colors against the current theme each build. Keep theme reads in the innermost widget (see `_ButtonSurface`) so interaction wrappers aren't rebuilt. When a color should fade in from transparent, use `color.withValues(alpha: 0)`, not `Color(0x00000000)` — lerping from transparent black flashes gray.

**Size animation.** The same restart problem applies to metrics, so sizes go through `MochiValueTransition<T>` (`widgets/value_transition.dart`): it eases between two values of any type over `motion.sizeDuration` and only restarts when the value itself changes, blending from wherever it currently is. The animated type needs value equality (`MochiButtonMetrics`), otherwise every rebuild counts as a change and the animation restarts forever. `MochiButton`, `MochiTile` and `MochiSwitch` use it for the `touch` ↔ desktop scale.

**Popover.** `MochiPopover` (`widgets/popover.dart`) is the base for menus, context menus and anything else anchored to a control. It wraps the widgets-layer `RawMenuAnchor` (master only), which mounts the panel in an `Overlay`, closes it on an outside tap or Escape, and restores focus to the anchor — so the widget itself only adds placement and the surface. Placement is a `SingleChildLayoutDelegate`: a `MochiPopoverSide` × `MochiPopoverAlign` against the anchor rect, a flip to the opposite side when the preferred one has no room (and only when the other side is genuinely roomier, otherwise the panel jumps about as its content resizes), then a clamp inside the overlay. The anchor builder is handed a `MochiPopoverAnchor` (`controller`, `focusNode`, `toggle`); wiring `focusNode` into the control is what makes focus return. `open(position:)` places the panel at an offset from the anchor's top left instead of against an edge, which is how a context menu opens at the pointer. Entering and leaving go through `MochiSurfaceTransition(scrim: false)` growing out of the anchored corner, and the overlay stays mounted until the exit animation finishes (`onCloseRequested` holds `hideOverlay` back).

**Menus.** `MochiMenu` (`widgets/menu.dart`) is a column of `MochiMenuItem`s (plus `MochiMenuDivider` / `MochiMenuLabel`) sized to its widest row by `IntrinsicWidth` and scrolling once it runs out of room. `MochiPopoverMenu` is the dropdown form, `MochiContextMenu` opens the same rows where the pointer is (right click, or long press — a child with its own long press wins the arena), and `MochiSubmenu` is a row that opens a menu beside it. An item runs its handler and then closes the *root* menu, found through a private `_MenuHost` that only the outermost menu installs, so choosing something in a submenu puts the whole thing away. Rows take a `MochiIntent`: anything but neutral is tinted at rest, not only while hovered, since the colour is what marks a destructive action out.

Two things about keys and menus, both from `RawMenuAnchor` putting the panel *beside* the anchor in the element tree rather than under it. First, arrow-key traversal is installed around the anchor, so a submenu's open key must be bound inside `MochiPopover.builder` (below that traversal, where the nearest binding wins) while its close key must be bound above `MochiPopover` (where the panel's own key events travel). Second, a `Shortcuts` or `CallbackShortcuts` placed inside the panel is *below* the focus that the panel takes, so it is never consulted. In tests, a touch tap leaves `FocusManager.highlightMode` in touch mode, where hover highlights and arrow traversal into a menu don't happen: open with `tester.tap(..., kind: PointerDeviceKind.mouse)`, and reuse one mouse gesture rather than adding a second pointer for the same device.

**Modals.** `MochiDialog` (`widgets/dialog.dart`) is the box; `MochiSheet` (`widgets/sheet.dart`) is the panel anchored to an edge. Both are shown by a `PopupRoute` (`MochiDialogRoute` / `MochiSheetRoute`) that reads its motion and barrier colour from the navigator's theme the way `MochiPageRoute` does, and enters with `MochiSurfaceTransition(scrim: false)` — the route's barrier does the dimming, over the whole screen rather than the surface's own box. Actions go in a row on the desktop scale and stack full width on touch, which is what apps otherwise wrap a dialog to do by hand. A sheet fills the screen across its own axis and shrink-wraps along it (so the column's `mainAxisSize` follows the axis), clears the system's edge padding itself since it runs to the edge, and dragging it towards that edge drives the route's own `AnimationController` backwards so the barrier fades with it. The `Align` lives *inside* `buildTransitions`, not in `buildPage`: a slide moves its child by a fraction of that child's size, so with a full-screen wrapper in between, both the animation and the drag would be measured against the screen rather than the sheet. Dismissing needs 48px of travel as well as half the sheet, so a short one can't be flicked away by a twitch — and the gesture is longer than that, since the recognizer eats the touch slop before the first update.

`showMochiModal` picks between the two from the breakpoint: a dialog from tablet width up, a bottom sheet on a phone. It takes the *parts* of the question (title / body / actions) rather than a built widget, because the two containers lay their actions out differently — which is also why there is no `Dialog.adaptive`: what adapts is the presentation, not the component. `showMochiConfirm` / `showMochiAlert` / `showMochiChoice` / `showMochiPrompt` are the ready-made questions built on it, with `MochiModalAction` as the button that pops the modal with a value; none of them are named after a dialog, since on a phone they aren't one. `showMochiPrompt`'s field owns its `TextEditingController` in a `State`, not the helper in a `try/finally`: the returned future completes when the route is popped, but the exit animation is still drawing the field, so disposing the controller then would break it. Its body is padded by `MochiFocusRing.outsetOf`, since a modal's body scrolls and a scroll view clips the ring.

**Toast.** `MochiApp` installs a `MochiToaster` above the navigator, so `showMochiToast` reaches it from anywhere, a toast outlives the page that raised it, and it paints over a dialog. Intent shows in the border, not the fill, and brings its own icon from `MochiIcons`. Hovering cancels the dwell timer (an Undo has to survive the pointer arriving) and leaving restarts it; the returned `MochiToastHandle` dismisses early. The stack has one width (`geometry.toastWidth`) rather than one per toast, which would jump as a longer message came and went. Tunable from `MochiApp`: `toastAlignment`, `maxVisibleToasts`, `maxQueuedToasts`, `toastWidth`.

**A toast's exit is two movements, and the queue is the toasts themselves.** Toasts raised past `maxVisible` wait their turn rather than pushing the oldest out, which would drop one nobody saw, and the waiting ones are drawn past the end of the stack — the real toasts, each giving up a little width and showing only its trailing edge (`_DeckPlace`). Leaving then goes: it slides towards the edge with the stack untouched, and only then does its place close. The front of the queue is promoted the moment that slide starts, and *stands where it was* — opaque, at its own place's size — so what the slide uncovers is the toast itself rather than a blank space; it grows up into the stack over the second half, at the mirror of the closing curve, so the stack below the gap moves up by exactly what it takes at the end and nothing above the gap moves at all. The places behind it hold until it goes (`reserved`), then move up with it. Several leaving at once each come up from the place they were standing at, not all from the front.

**Motion you can't see is motion you can't fix.** X11 screenshots can't see the Linux window under Wayland, so work on the toaster went several rounds of plausible-sounding blind edits that were wrong. What settled it: a throwaway `lib/main_toast.dart` with nothing but toasts on a timer and the durations slowed to two or three seconds, run with `fvm flutter run -d web-server --web-port 8080 -t lib/main_toast.dart` and watched in a browser a frame at a time. Do that first next time. Two habits from the same episode: prefer `Edit` over scripted string replacement (a reformat silently breaks the match and the "fix" never lands), and check a new test actually fails without the fix.

**Text fields.** `MochiTextField` (`widgets/text_field.dart`) is an `EditableText` with `rendererIgnoresPointer: true` inside a `TextSelectionGestureDetectorBuilder`'s detector that wraps the whole box, so a tap on the padding focuses it too and clicks, double clicks, drags and right clicks select the way platform fields do. It takes a `MochiButtonMetrics` for its `size`, and the box has the button's height as a minimum with a single line centred in it, so a field and a button in one row line up — computing the padding from the text's line height came out a few pixels short. The context menu is `contextMenuBuilder` → `MochiPopoverSurface` + `MochiMenu`, placed by `DesktopTextSelectionToolbarLayoutDelegate` and wrapped in `TextFieldTapRegion`, so pressing an item doesn't count as a tap outside the field and steal its focus first; its labels come from `MochiStrings`, and it always lists the same four edits, greyed out when they don't apply, rather than rows that come and go with the selection (on Linux a right click outside the selection moves the caret first, so cut and copy would otherwise vanish). A single-line field has no vertical padding, only the minimum height centring it, so the clear button appearing can't make the box grow. On web the browser's own context menu takes over (Flutter's default), so check the menu in a test on a desktop platform, not in the browser. A synthetic Enter from a browser automation tool never reaches Flutter's hidden DOM input either, so `onSubmitted` looks dead there: dispatch a real `keydown` on `document.activeElement` from the console to try it. Touch selection handles are a small `TextSelectionControls` (a dot under each end), shown by the same rule `TextField` uses.

**Field frame.** `MochiFieldFrame` (`widgets/field_frame.dart`) is the label above a box and the description, error or counter below it, shared by the text field, the select and the autocomplete so a form lines up and an app's own field can wear the same thing. It stretches its children to the width it is given and, with no bounded width to give (a row of code boxes, a select in a row), lines them up at the start instead: a stretched child under an unbounded width would be handed a tight infinite one.

**Selects.** `MochiSelect` / `MochiMultiSelect` (`widgets/select.dart`) share a private `_SelectField`: the box is a `MochiTappable` drawn like a `MochiTextField` of the same size (same metrics, border colours, label / description / error), and the list is a `MochiPopoverMenu` with `matchAnchorWidth`. Options are `MochiSelectOption`s with a `String` label, because the label is also what the field (or a multi-select's badge) shows. A row's check is always laid out and only faded in, so ticking a row in a multi-select can't widen the list. Opening from the keyboard focuses the chosen row (`MochiMenuItem.autofocus`); opening with the pointer doesn't, or the row would show a focus ring nobody asked for. Telling the two apart is a `Listener` flag that is cleared in a microtask after the pointer's release, since the tap that opens the list fires after the `Listener` sees the up event. With an unbounded width the field sizes itself to its longest option (a `TextPainter` measure behind a `LayoutBuilder`), like the stepper, so it doesn't change width with the choice.

**Searching.** `MochiSearchBar` (`widgets/search_bar.dart`) is a `MochiTextField` with the magnifier, the × and a debounce. Two callbacks, because they answer different questions: `onChanged` is every keystroke (what the field says), `onSearch` is the query worth running (after the typing stops, or at once on submit or on a clear — waiting to show everything again only reads as slow). It remembers the last query it dispatched, so a submit after the timer has already fired doesn't search twice, and a query typed and taken back inside the debounce never runs at all. `loading` swaps the × for a spinner in the same place rather than adding one beside it. Suggestions are not part of it: that is `MochiAutocomplete` with a magnifier as its prefix.

**One-time codes.** `MochiOtpField` (`widgets/otp_field.dart`) is one `EditableText` holding the whole code, hidden in a 1×1 box behind a row of drawn boxes — not a field per box, which would have to split a paste by hand and chase the focus about. The caret can only be at the end (a listener puts the selection back there), so a character always lands in the next empty box and backspace always takes the last one out; the platform's `oneTimeCode` autofill fills it like any other field. The boxes take the pointer and hand focus to the hidden field, which has `rendererIgnoresPointer` and no selection, handles or context menu of its own. The box being filled paints its own caret, a blinking bar that stops under `MediaQuery.disableAnimations`.

**Autocomplete.** `MochiAutocomplete` (`widgets/autocomplete.dart`) wraps the widgets layer's `RawAutocomplete`, which on master mounts the list through `OverlayPortal.overlayChildLayoutBuilder` and hands it the field's width and the room below, so the panel only has to fill what it is given (a `SizedBox(width: double.infinity)` inside the height cap). Unlike a select, the text is what counts: anything can be typed, `onChanged` reports every keystroke and `onSelected` only fires for an option. The frame is *outside* the `RawAutocomplete`, so the list hangs from the box rather than from below a description — which is also why there is no `maxLength`, whose counter would sit between the two. The rows are `MochiMenuItem`s with no focus of their own (`RawAutocomplete` keeps the panel out of traversal): the arrows move a highlight index, read through `AutocompleteHighlightedOption.of`, and the highlighted row is marked `selected`; a `GlobalKey` per row lets the panel `Scrollable.ensureVisible` it as the arrows walk past the end.

**Tooltip.** `MochiTooltip` (`widgets/tooltip.dart`) wraps Flutter's widgets-layer `RawTooltip`, adding a theme-styled bubble (inverse `neutral` tone), a `positionDelegate` that places it above/below the child instead of over its center, and keyboard-focus support (RawTooltip has none). `MochiButton(tooltip:)` is a shorthand. On touch, a descendant `onLongPress` wins the gesture arena over the tooltip's long-press trigger.

**Scrollbars.** `MochiScrollBehavior` installs `MochiScrollbar` on desktop platforms: a rounded thumb, always visible, thickening from 6 to 11 once the pointer comes within 32px of it and for the whole of a drag (tracked through a global pointer route, since the release can happen anywhere). Its `Listener` is `translucent`: the `MouseRegion` under it is not opaque, so deferring to the child would keep it out of the hit-test path. Containers that scroll (`MochiCard`, `MochiTileGroup`) clip their content so the thumb stays inside the rounded corners.

**Wheel containment.** `MochiScrollArea(containScroll: true)` (the default) keeps a mouse wheel over the area from scrolling the page behind once the area hits its end. A wheel event goes to the first scrollable on the hit path that registers with `GestureBinding.pointerSignalResolver`, and a `Scrollable` only registers while it can still move; so at the end the area registers a do-nothing handler ahead of whatever lies further out. It does so only while its content overflows, and only along its own axis, so an area that fits never blocks the page. Its `Listener` has to be `translucent`: on desktop the scrollbar wraps the list in a `MouseRegion(opaque: false)`, and a non-opaque `RenderMouseRegion` reports "not hit" to its parent even when its child was, so a `deferToChild` ancestor silently drops out of the hit path. The Android-default tests missed this; the regression test runs under `TargetPlatformVariant.only(TargetPlatform.linux)`. Test desktop-only chrome on a desktop platform. Touch and trackpad drags don't chain in the first place: the inner scrollable wins the whole gesture.

**Bounded constraints.** `MochiDivider` and `MochiLinearProgress` expand along their axis and need a bounded parent. Watch for widgets that silently shrink instead: a `FractionallySizedBox` under loose constraints sizes to its child, which once pinned the indeterminate progress bar in place. When something "doesn't animate", check the on-screen geometry (log `RenderBox.localToGlobal`) before trusting a screenshot — X11 captures of the GL window and the browser pane can both be stale.

**Sizes.** One `MochiSize` enum (`xs, sm, md, lg`) is the size axis of every component that has one; what each step measures lives in that component's `XxxMetrics` (`MochiButtonMetrics`, `MochiCloseButtonMetrics`, `MochiBadgeMetrics`, and `MochiProgressMetrics`, which the ring and the bar share so a size means the same weight for both), which needs value equality to go through `MochiValueTransition`. A badge defaults to `sm`, a step under a control, since it sits beside text.

**Joined groups.** `MochiBadgeGroup` follows the `MochiTileGroup` pattern: an InheritedWidget tells each child its place (only / start / middle / end), and the child squares off its own inner corners with a `BorderRadiusDirectional`. Neighbouring borders are shared by pulling each later badge back over the previous one by the border width (a private `_Overlap` render box — a negative margin, which neither `Padding` nor `Row.spacing` allows), mirrored for right-to-left. In tests, a `Directionality` placed *around* `MochiApp` is overridden by the one `WidgetsApp` installs; put it inside `home`.

**Collapsing.** `MochiCollapsible` (`widgets/collapsible.dart`) is the one way things open and close under a header — `MochiCard.collapsible` now, an accordion and sidebar groups later. The body grows with `Align(heightFactor:)` inside a `ClipRect` over `motion.sizeDuration` / `sizeCurve`. It is uncontrolled from `initiallyExpanded`, or controlled by `expanded`, where a press only calls `onExpandedChanged` and the widget follows what it is rebuilt with (that is how an accordion keeps one open). With `maintainState`, the body keeps the *same* widget tree open and closed (an `Offstage` that toggles, not a different parent), otherwise its state is lost on the swap; a closing body is wrapped in `ExcludeFocus`. The header tints rather than grows, and its focus ring is `inset` because whatever holds it (a card) clips. A collapsible card moves its padding inside, so the title row's hover fill reaches the card's edges, and puts a `divider` under the title row with the body fully padded below it: letting the row's bottom padding stand in for the gap looks right at rest but, once hovered, the fill runs straight into the content.

**Components so far.** `MochiTappable`, `MochiButton` (+`.icon`), `MochiTooltip`, `MochiFocusRing`, `MochiDivider`, `MochiCard`, `MochiBadge`, `MochiSwitch`, `MochiCircularProgress`, `MochiLinearProgress`, `MochiTile`/`MochiTileGroup`, `MochiHeader`/`MochiHeaderAction`, `MochiScaffold`, `MochiScrollArea`, `MochiPopover`, `MochiMenu` (+`MochiPopoverMenu`/`MochiContextMenu`/`MochiSubmenu`), `MochiDialog`, `MochiSheet`, `MochiToast`, `MochiBadgeGroup`, `MochiCollapsible`, `MochiTextField`, `MochiSelect`/`MochiMultiSelect`, `MochiAutocomplete`, `MochiOtpField`, `MochiSearchBar`, `MochiCheckbox`, `MochiStepper` (keeps the last value it sent until the parent rebuilds with it: a held button or key steps faster than frames arrive, and each step must build on the previous one rather than on `widget.value`), `MochiRadioGroup`/`MochiRadio` (the widgets layer's `RadioGroup` + `RawRadio` underneath, which bring arrow-key selection, a single tab stop and mutually-exclusive semantics; `appearance: .card` is the radio card), `MochiCloseButton` (takes its colour from the ambient `IconTheme`, not an intent, so it reads right inside whatever it closes; `shape: .rounded` by default, matching an icon button's corners, and `.circle` inside a badge). Each one: theme reads in the innermost widget, colors via `MochiStateTransition`, shapes via `MochiSuperellipseBorder`, sizes from `theme.touch`, and `MediaQuery.disableAnimations` honored by anything that animates on its own. Verify new components in the real app in **debug** mode (`fvm flutter run -d linux`): profile builds have assertions off, so unbounded-constraint mistakes render as silently missing widgets instead of errors.

**Responsive.** `theme/responsive.dart` defines `MochiBreakpoint` (content width + 24px gutters: 768 / 1008 / 1248, plus 1600 for fullhd) and `MochiScreenSize`. `ResponsiveScope` can override the size; otherwise it's derived from `MediaQuery` width. Use `context.responsive(mobile: ..., desktop: ...)` for values or the `Responsive` widget for builders — both fall back to the nearest smaller tier.
